# 132. 필터를 실제 던전과 모바일에 연결하기

**목표:** 싸우며 표시 등급을 바꿉니다.

## 한눈에 보는 기능의 흐름

표시 등급 선택 → 이름표 갱신 → 이동하며 토글 → 숨긴 아이템 줍기

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“필터를 실제 던전과 모바일에 연결하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 검사된 필터 정책야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 관찰 가능한 기준으로 확인

**내가 만든 하네스의 실제 경로와 현재 게임 후보를 확인하고 game-feature로 이 작업을 처리해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 02. 구현과 판정의 책임 나누기

**필요한 담당 역할만 고르고 구현·QA·독립 검토를 분리해 줘.**

왜 이렇게 요청하나요? 구현자가 자신의 설명만으로 완료를 결정하면 놓친 가정을 그대로 통과시킬 수 있습니다. 원래 요구·실제 변경·테스트를 다른 관점에서 검토하고 쓰기 권한을 나눕니다.

#### 03. 작성한 도구를 실제로 사용

**변경안·승인한 후보·Unity 통합·현재 소스 검사를 실제로 연결하고, 참고 완성본으로 우회하지 마.**

왜 이렇게 요청하나요? 참고 완성본으로 몰래 실행하면 현재 만든 하네스의 누락이나 오류가 드러나지 않습니다. 실행 경로를 확인해 지금 개발한 도구가 작업과 검사를 수행하도록 합니다.

#### 04. 구현할 결과와 조건 고정

**정책을 기존 드롭 이름표와 설정 화면에 연결해 줘.**

왜 이렇게 요청하나요? “정책을 기존 드롭 이름표와 설정 화면에 연결해 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 싸우며 표시 등급을 바꿉니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 05. 표시와 아이템 존재 분리

**새 필터 시스템을 따로 복제하지 말고 실제 이름표 생성과 풀 재사용 경로에서 호출해 줘.**

왜 이렇게 요청하나요? 이름표를 숨기는 기능이 아이템 자체를 끄거나 삭제하면 줍기·퀘스트·저장까지 달라집니다. 보기 편하게 하는 정책은 소유 데이터와 획득 기능을 바꾸지 않게 분리합니다.

#### 06. 표시와 아이템 존재 분리

**풀에서 일반 장비 이름표를 퀘스트 이름표로 재사용할 때 이전 숨김 상태가 남지 않게 해 줘.**

왜 이렇게 요청하나요? 이름표를 숨기는 기능이 아이템 자체를 끄거나 삭제하면 줍기·퀘스트·저장까지 달라집니다. 보기 편하게 하는 정책은 소유 데이터와 획득 기능을 바꾸지 않게 분리합니다.

#### 07. 같은 요청의 반복 처리 정의

**씬 연결은 반복 실행 가능한 Editor API 도구로 제안하고 broker를 통해 실행해 줘.**

왜 이렇게 요청하나요? 클릭 연타·재연결·중복 이벤트는 개발과 플레이 중 모두 발생할 수 있습니다. 반복돼도 한 번 처리해야 하는 결과와 매번 새로 처리할 결과를 나눠 데이터가 누적되지 않게 합니다.

#### 08. 끊긴 입력과 작업 정리

**PC 포커스 상실과 Android 이동+전체 보기 동시 입력을 검사해 줘.**

왜 이렇게 요청하나요? 앱 전환이나 창 닫기에서는 정상적인 손 떼기 이벤트가 오지 않을 수 있습니다. 중단 시 눌림·예약·임시 효과를 정리해야 복귀 후 멋대로 움직이거나 공격하지 않습니다.

#### 09. 보여 준 자료의 한계 구분

**화면 캡처만으로 멀티터치 검사를 대체하지 마.**

왜 이렇게 요청하나요? 사진 한 장은 입력·저장·시간에 따른 동작까지 증명하지 못하고, 정해진 모의 응답은 실제 서비스 호출이 아닙니다. 각각 확인할 수 있는 범위만 기록하게 하는 요청입니다.

#### 10. 아래 항목을 완료 조건으로 사용

**이 기능의 규칙:**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

#### 11. 관찰 가능한 기준으로 확인

**순수 테스트가 통과해도 UI가 정책을 호출하지 않으면 기능은 없는 것과 같다.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 12. 구현할 결과와 조건 고정

**기존 이름표가 생성되는 지점, 풀에서 돌아오는 지점, 설정이 바뀌는 지점에 같은 정책을 연결한다.**

왜 이렇게 요청하나요? “기존 이름표가 생성되는 지점, 풀에서 돌아오는 지점, 설정이 바뀌는 지점에 같은 정책을 연결한다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 싸우며 표시 등급을 바꿉니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 13. 필터가 바뀔 때만 표시 갱신

**매 프레임 모든 드롭을 검색하지 말고 등록된 이름표에 설정 변경 이벤트를 전달한다.**

왜 이렇게 요청하나요? 설정이 그대로인데 매 프레임 드롭 전체를 찾으면 불필요한 작업이 생깁니다. 등록된 이름표가 설정 변경과 생성·제거 사건에 반응하도록 하되, 새 드롭에도 현재 필터를 즉시 적용합니다.

#### 14. UI 입력과 월드 입력 분리

**UI에서 누른 입력이 바닥 이동이나 공격으로 새지 않아야 한다.**

왜 이렇게 요청하나요? 가방 버튼을 누른 입력이 뒤의 바닥 클릭으로도 처리되면 캐릭터가 원치 않게 이동하거나 공격합니다. 입력이 시작된 대상을 구분해 한 행동이 서로 다른 명령으로 중복 처리되지 않게 합니다.

#### 15. 동시 입력을 서로 독립적으로 유지

**모바일에서는 ‘전체 보기’를 누르고 조이스틱을 놓아야만 움직일 수 있는 구조를 만들지 않는다.**

왜 이렇게 요청하나요? 한 손가락을 떼었을 때 다른 손가락의 이동까지 해제되면 모바일 전투가 끊깁니다. 입력의 주체와 눌림 상태를 따로 관리하고 실제 두 손가락 조합으로 검사해야 합니다.

#### 16. 끊긴 입력과 작업 정리

**PC에서 창 포커스를 잃었을 때 임시 표시 키가 계속 눌린 상태로 남지 않게 초기화한다.**

왜 이렇게 요청하나요? 앱 전환이나 창 닫기에서는 정상적인 손 떼기 이벤트가 오지 않을 수 있습니다. 중단 시 눌림·예약·임시 효과를 정리해야 복귀 후 멋대로 움직이거나 공격하지 않습니다.

#### 17. 구현할 결과와 조건 고정

**통합 역할은 Editor 도구를 만들고 등록된 integrate 명령만 실제 씬을 수정한다.**

왜 이렇게 요청하나요? “통합 역할은 Editor 도구를 만들고 등록된 integrate 명령만 실제 씬을 수정한다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 싸우며 표시 등급을 바꿉니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 18. 표시와 아이템 존재 분리

**도구를 두 번 실행해도 버튼·이벤트 구독·필터 관리자 인스턴스가 중복되지 않아야 한다.**

왜 이렇게 요청하나요? 이름표를 숨기는 기능이 아이템 자체를 끄거나 삭제하면 줍기·퀘스트·저장까지 달라집니다. 보기 편하게 하는 정책은 소유 데이터와 획득 기능을 바꾸지 않게 분리합니다.

#### 19. 자산 참조의 정체성 보존

**import와 .meta 생성이 끝나기 전에 seal하면 다음 자동 검사에서 소스 변경이 감지되는 것이 정상이다.**

왜 이렇게 요청하나요? Unity는 자산을 파일 이름만으로 식별하지 않습니다. 메타 정보가 바뀌면 같은 이름의 파일이 있어도 참조가 끊길 수 있어 파일과 식별자를 함께 관리해야 합니다.

#### 20. 구현과 실행은 AI에게 맡기기

#### 03. 원인 하나를 좁혀 수정

**최소 수정 뒤 같은 재현과 관련 정상 동작을 다시 검사해 줘.**

왜 이렇게 요청하나요? 오류 수정 중 새 기능까지 넣으면 어떤 변경이 문제를 해결하거나 악화했는지 알기 어렵습니다. 원래 재현을 보존하고 작은 변경 뒤 같은 입력과 주변 정상 동작을 다시 확인합니다.

#### 04. 실패도 재현 자료로 보존

**실패 기록은 지우지 마.**

왜 이렇게 요청하나요? 실패한 입력과 로그가 있어야 같은 문제가 다시 생겼을 때 비교할 수 있습니다. 성공 기록으로 덮어쓰지 않고 전후 자료를 남기면 무엇을 고쳤는지 확인할 수 있습니다.

<details>
<summary>보낼 원문 전체 — 설명은 복사되지 않습니다</summary>

```text
새 정책만 검사하지 말고 현재 씬의 이름표 생성·풀 반환·토글 입력을 함께 재현해 줘.
새 기능을 추가하지 말고 현재 오류와 실제 로그를 먼저 읽어 줘. 최소 수정 뒤 같은 재현과 관련 정상 동작을 다시 검사해 줘. 실패 기록은 지우지 마.
```

</details>

## 새 세션에서 이어가기

### AI에게 보낼 요구와 이유

#### 01. 이어서 할 작업 식별

**“필터를 실제 던전과 모바일에 연결하기” 작업을 이어가고 싶어.**

왜 이렇게 요청하나요? 이름으로 재개할 작업을 찾고, 뒤에 이어지는 요청으로 실제 파일·진행 중 작업·기록을 다시 읽게 합니다. 제목만 보고 이전 상태를 기억한다고 가정하지 않습니다.

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

<details>
<summary>보낼 원문 전체 — 설명은 복사되지 않습니다</summary>

```text
“필터를 실제 던전과 모바일에 연결하기” 작업을 이어가고 싶어. 실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘. 진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘. 기존 성공과 실패 기록은 보존해 줘.
```

</details>

## 왜 이렇게 만드는가

순수 테스트가 통과해도 UI가 정책을 호출하지 않으면 기능은 없는 것과 같다. 기존 이름표가 생성되는 지점, 풀에서 돌아오는 지점, 설정이 바뀌는 지점에 같은 정책을 연결한다. 매 프레임 모든 드롭을 검색하지 말고 등록된 이름표에 설정 변경 이벤트를 전달한다.

UI에서 누른 입력이 바닥 이동이나 공격으로 새지 않아야 한다. 모바일에서는 ‘전체 보기’를 누르고 조이스틱을 놓아야만 움직일 수 있는 구조를 만들지 않는다. PC에서 창 포커스를 잃었을 때 임시 표시 키가 계속 눌린 상태로 남지 않게 초기화한다.
