# 139. 재료로 장비 제작하기

**목표:** 가방 공간과 재료가 맞을 때만 제작됩니다.

**시작 상태:** 분해·재료 지갑·거래 서비스

## 한눈에 보는 기능의 흐름

레시피 선택 → 재료·가방 검사 → 한 거래로 제작 → 요청 ID 기록

![재료로 장비 제작하기 — 개념 설명용 구조](../lesson_visuals/139.svg)

**경계:** 같은 요청이 결과 장비를 두 번 만들지 않기

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“재료로 장비 제작하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 분해·재료 지갑·거래 서비스야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 관찰 가능한 기준으로 확인

**내가 만든 하네스의 실제 경로와 현재 게임 후보를 확인하고 game-feature로 이 작업을 처리해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 02. 구현과 판정의 책임 나누기

**필요한 담당 역할만 고르고 구현·QA·독립 검토를 분리해 줘.**

왜 이렇게 요청하나요? 구현자가 자신의 설명만으로 완료를 결정하면 놓친 가정을 그대로 통과시킬 수 있습니다. 원래 요구·실제 변경·테스트를 다른 관점에서 검토하고 쓰기 권한을 나눕니다.

#### 03. 작성한 도구를 실제로 사용

**변경안·승인한 후보·Unity 통합·현재 소스 검사를 실제로 연결하고, 참고 완성본으로 우회하지 마.**

왜 이렇게 요청하나요? 참고 완성본으로 몰래 실행하면 현재 만든 하네스의 누락이나 오류가 드러나지 않습니다. 실행 경로를 확인해 지금 개발한 도구가 작업과 검사를 수행하도록 합니다.

#### 04. 거래·보상의 전체 성공 보장

**대장간 기본 장비 레시피3개를 추가해 줘.**

왜 이렇게 요청하나요? 재료 차감과 결과 지급이 따로 성공하면 손해나 복제가 생깁니다. 조건을 먼저 검사하고 한 거래로 반영하며 같은 요청을 다시 받아도 두 번 지급하지 않게 합니다.

#### 05. 기존 결과를 보호

**기존 아이템18종은 유지하고 신규 ID 만 사용해 줘.**

왜 이렇게 요청하나요? 새 작업이 이미 정상인 기능이나 자산까지 바꾸면 원인을 추적하기 어렵습니다. 유지할 대상을 명시해 변경 전후를 비교하고 원치 않은 영향을 찾습니다.

#### 06. 무작위 결과를 재현 가능하게

**미리보기에서는 ID 생성과 재료 차감·난수 사용을 하지 마.**

왜 이렇게 요청하나요? 실패한 맵이나 전리품 결과를 다시 만들 수 있어야 원인을 고칠 수 있습니다. 생성 버전·설정·시드를 함께 기록하고 지형·장식·보상 난수를 분리해 작은 변경의 파급을 줄입니다.

#### 07. 종료 이후의 상태까지 확인

**성공 커밋 한 번에 재료 차감·아이템 추가·revision 증가·영수증을 저장해 줘.**

왜 이렇게 요청하나요? 현재 화면에서 맞는 값도 저장하거나 다시 구성할 때 빠질 수 있습니다. 실제 종료·불러오기 전후에 ID·옵션·장착·진행을 비교해야 유지되는 범위를 확인할 수 있습니다.

#### 08. 늦게 온 결과가 최신 작업을 덮지 않기

**동일 requestId는 동일 결과 ID를 돌려주고, payload가 바뀌면 거부해 줘.**

왜 이렇게 요청하나요? AI 생성이나 다운로드가 진행되는 동안 원본과 선택이 바뀔 수 있습니다. 요청 ID·기준 버전·취소 상태를 대조해야 이전 결과가 최신 편집을 덮어쓰지 않습니다.

#### 09. 이동에 실패해도 아이템 보존

**가방이 가득 차면 거래 전체를 거부하고 재료를 유지해 줘.**

왜 이렇게 요청하나요? 줍기·보관·장착은 한 물건의 위치를 바꾸는 작업입니다. 목적지 공간이 없거나 취소됐을 때 원래 위치를 먼저 지우지 않아야 아이템 분실과 복제를 막습니다.

#### 10. 거래·보상의 전체 성공 보장

**기존 분해와 제작이 같은 거래 서비스의 규칙을 쓰게 해 줘.**

왜 이렇게 요청하나요? 재료 차감과 결과 지급이 따로 성공하면 손해나 복제가 생깁니다. 조건을 먼저 검사하고 한 거래로 반영하며 같은 요청을 다시 받아도 두 번 지급하지 않게 합니다.

#### 11. 아래 항목을 완료 조건으로 사용

**이 기능의 규칙:**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

#### 12. 구현할 결과와 조건 고정

**대장간 장비는 무기·갑옷·장신구 하나씩 세 개만 추가한다.**

왜 이렇게 요청하나요? “대장간 장비는 무기·갑옷·장신구 하나씩 세 개만 추가한다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 가방 공간과 재료가 맞을 때만 제작됩니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 13. 구현할 결과와 조건 고정

**제작검은 고철6+불씨2, 제작갑옷은 고철8+불씨1, 제작장신구는 고철3+가루3을 소비한다.**

왜 이렇게 요청하나요? “제작검은 고철6+불씨2, 제작갑옷은 고철8+불씨1, 제작장신구는 고철3+가루3을 소비한다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 가방 공간과 재료가 맞을 때만 제작됩니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 14. 전투 수치를 한 규칙으로 계산

**초기 보너스는 각각 공격력4, 방어력3, 최대 마나5다.**

왜 이렇게 요청하나요? 표시와 실제 피해 계산이 다르면 장비·레벨·스킬 효과를 믿을 수 없습니다. 경계값과 사망·회복 조건을 명확히 정하고 숫자와 체력바를 함께 비교합니다.

#### 15. 아이템 정의와 콘텐츠 ID의 적용 조건

**기존 18종 아이템 정의를 바꾸지 않고 새 ID를 추가한다.**

왜 이렇게 요청하나요? 아이템 정의는 “어떤 종류의 물건인가”를 설명합니다. 콘텐츠 ID는 그 정의를 찾는 안정된 식별자입니다. 표시 이름은 번역·밸런스 수정으로 바뀔 수 있으므로 ID와 나눕니다. 정의 ID와 소유한 한 자루의 instanceId를 같은 값으로 쓰지 않습니다.

#### 16. 기계가 읽을 값의 형식 검사

**보너스가 기존 데이터의 어느 필드에 들어갈지는 실제 구조에 맞춰 확정한다.**

왜 이렇게 요청하나요? 문자열이 JSON으로 읽힌다고 업무 규칙까지 올바른 것은 아닙니다. 필드·타입·범위·참조를 검사해 잘못된 값이 실제 코드·저장·편집기로 들어오지 않게 합니다.

#### 17. 종료 이후의 상태까지 확인

**첫 제작은 결과 능력치를 고정해 무작위 재추첨과 저장 악용을 줄인다.**

왜 이렇게 요청하나요? 현재 화면에서 맞는 값도 저장하거나 다시 구성할 때 빠질 수 있습니다. 실제 종료·불러오기 전후에 ID·옵션·장착·진행을 비교해야 유지되는 범위를 확인할 수 있습니다.

#### 18. 종류와 실제 소유 물건 구분

**미리보기는 결과 정의·재료 비용·남을 공간만 계산하며 instanceId나 RNG를 소비하지 않는다.**

왜 이렇게 요청하나요? 같은 종류의 검 두 자루도 옵션과 소유 위치는 별개입니다. 정의 데이터와 개별 아이템을 나누면 한 물건을 수정했을 때 다른 물건과 원본 규격까지 바뀌지 않습니다.

#### 19. 종류와 실제 소유 물건 구분

**실제 커밋 때 새 instanceId를 한 번 생성하고 영수증에 저장한다.**

왜 이렇게 요청하나요? 같은 종류의 검 두 자루도 옵션과 소유 위치는 별개입니다. 정의 데이터와 개별 아이템을 나누면 한 물건을 수정했을 때 다른 물건과 원본 규격까지 바뀌지 않습니다.

#### 20. 거래·보상의 전체 성공 보장

**같은 requestId에 다른 레시피를 넣으면 이전 결과로 성공시키지 말고 request payload 충돌로 거부한다.**

왜 이렇게 요청하나요? 재료 차감과 결과 지급이 따로 성공하면 손해나 복제가 생깁니다. 조건을 먼저 검사하고 한 거래로 반영하며 같은 요청을 다시 받아도 두 번 지급하지 않게 합니다.

## 왜 이렇게 만드는가

대장간 장비는 무기·갑옷·장신구 하나씩 세 개만 추가한다. 제작검은 고철6+불씨2, 제작갑옷은 고철8+불씨1, 제작장신구는 고철3+가루3을 소비한다. 초기 보너스는 각각 공격력4, 방어력3, 최대 마나5다. 기존 18종 아이템 정의를 바꾸지 않고 새 ID를 추가한다. 보너스가 기존 데이터의 어느 필드에 들어갈지는 실제 구조에 맞춰 확정한다.

첫 제작은 결과 능력치를 고정해 무작위 재추첨과 저장 악용을 줄인다. 미리보기는 결과 정의·재료 비용·남을 공간만 계산하며 instanceId나 RNG를 소비하지 않는다. 실제 커밋 때 새 instanceId를 한 번 생성하고 영수증에 저장한다. 같은 requestId에 다른 레시피를 넣으면 이전 결과로 성공시키지 말고 request payload 충돌로 거부한다.
