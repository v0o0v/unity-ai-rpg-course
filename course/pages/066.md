## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“타일 경계와 랜덤맵 외형 연결하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 타일 샘플과 랜덤 Layout야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**현재 프로젝트의 실제 파일과 이미 결정한 규칙을 먼저 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 실제 사용 중인 코드에 연결

**이름이 다른 기존 구현이 있으면 새로 중복 제작하지 말고 그 구현에 연결해 줘.**

왜 이렇게 요청하나요? 예제와 이름이 다르더라도 현재 씬과 입력에서 호출하는 구현이 작업 대상입니다. 같은 기능을 새로 만들기보다 기존 진입점을 확인해 수정이 실제 게임에 반영되고 중복 실행되지 않게 합니다.

#### 03. 자동 타일링·Rule Tile·경계 마스크의 적용 조건

**현재 2D 랜덤맵에 자동 타일링과 선택한 타일 아트를 연결해 줘.**

왜 이렇게 요청하나요? 자동 타일링은 주변 칸이 바닥인지 벽인지에 따라 모서리·직선·끝 타일을 고르는 규칙입니다. 지형의 연결을 새로 만드는 알고리즘과는 다릅니다. 자연스러운 경계 그림과 실제 이동 가능성은 별개입니다.

#### 04. 기존 결과를 보호

**기본은 직사각형 타일맵으로 유지해 줘.**

왜 이렇게 요청하나요? 새 작업이 이미 정상인 기능이나 자산까지 바꾸면 원인을 추적하기 어렵습니다. 유지할 대상을 명시해 변경 전후를 비교하고 원치 않은 영향을 찾습니다.

#### 05. 관찰 가능한 기준으로 확인

**북1·동2·남4·서8의16개 경계 마스크와 누락 시 대체 타일을 만들고 실제 테스트 보드를 보여 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 06. 무작위 결과를 재현 가능하게

**장식 변형은 장식 시드와 셀 좌표만 사용하고 지도·전리품 난수는 소비하지 마.**

왜 이렇게 요청하나요? 실패한 맵이나 전리품 결과를 다시 만들 수 있어야 원인을 고칠 수 있습니다. 생성 버전·설정·시드를 함께 기록하고 지형·장식·보상 난수를 분리해 작은 변경의 파급을 줄입니다.

#### 07. 점이 아니라 몸체가 지나가게 하기

**큰 벽 그림과 실제 차단 셀을 분리하고 A*·몸체 반경·스폰은 보존해 줘.**

왜 이렇게 요청하나요? 길의 중심점이 연결돼 있어도 반경이 있는 캐릭터는 모서리나 좁은 문에 걸릴 수 있습니다. 실제 몸체 크기로 통과·차단을 확인해야 길찾기 그림과 플레이 결과가 맞습니다.

#### 08. 앞뒤를 그리는 기준 정하기

**3×3 반복 이음새, 마스크16개, 생성 시드100개의 매핑 누락과 실제 앞뒤 정렬을 검사해 줘.**

왜 이렇게 요청하나요? 2D 그림의 화면상 겹침 순서와 물리 충돌은 별개입니다. 바닥·배우·높은 장식의 정렬 기준을 나눠야 캐릭터가 기둥 앞뒤를 오갈 때 자연스럽게 가려집니다.

#### 09. 탑다운·쿼터뷰·아이소메트릭의 적용 조건

**아이소메트릭 표현은 내가 별도로 요청할 때만 사본에서 선택 작업으로 진행해 줘.**

왜 이렇게 요청하나요? 탑다운은 위에서 내려다보는 플레이 방식, 쿼터뷰는 비스듬히 보이는 시각 표현을 가리킬 때 쓰입니다. 아이소메트릭은 일정 축척의 축 방향을 사용하는 표현·격자 방식입니다. 2.5D는 다양한 혼합 표현을 통칭합니다. 쿼터뷰풍 캐릭터 그림을 썼다는 이유로 3D Collider를 붙이지 않습니다.

#### 10. 앞뒤를 그리는 기준 정하기

**격자 변환·클릭·발 정렬·방향 속도를 함께 검사하고 기본 게임에 자동으로 합치지 마.**

왜 이렇게 요청하나요? 2D 그림의 화면상 겹침 순서와 물리 충돌은 별개입니다. 바닥·배우·높은 장식의 정렬 기준을 나눠야 캐릭터가 기둥 앞뒤를 오갈 때 자연스럽게 가려집니다.

#### 11. 구현과 실행은 AI에게 맡기기

**코드·설정·파일 생성·실행은 네가 맡고, 필요한 화면과 결과를 보여 줘.**

왜 이렇게 요청하나요? 설명이나 코드 조각만 받으면 실제 파일 생성·연결·실행이 빠질 수 있습니다. AI가 개발 작업까지 수행하고, 사람은 요구·승인·결과 판단을 맡도록 역할을 분명히 합니다.

#### 12. 막힌 준비를 먼저 해결

**수행하지 못한 작업과 필요한 승인·도구 연결은 구분해서 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 3. 결과를 직접 확인하기

먼저 확인 요청을 보내 AI가 검사와 화면을 준비하게 하세요. 그다음 아래 동작을 하나씩 확인합니다.

### AI에게 보낼 요구와 이유

#### 01. 검사할 입력과 관찰 지점 준비

**방금 구현한 기능의 자동 검사와 확인 화면을 준비해 줘.**

왜 이렇게 요청하나요? 정상 예 하나만 보면 실패 조건을 놓치기 쉽습니다. 정상·경계·반례를 실제 입력으로 준비하고 사람이 볼 화면도 맞춰 확인 범위를 분명하게 합니다.

#### 02. 결과를 재확인할 근거 남기기

**정상 동작과 아래 실패 조건을 실제로 검사하고 대상·실행 수·결과를 보여 줘.**

왜 이렇게 요청하나요? “잘 됩니다”라는 요약만으로는 어떤 입력과 버전을 검사했는지 알 수 없습니다. 대상·실행 수·실패 내용·파일을 함께 남겨 같은 조건으로 다시 확인할 수 있게 합니다.

#### 03. 기존 결과를 보호

**16개 마스크가 누락 없이 표시되고, 아트를 끄거나 켜도 같은 지형과 전리품이 유지된다.**

왜 이렇게 요청하나요? 새 작업이 이미 정상인 기능이나 자산까지 바꾸면 원인을 추적하기 어렵습니다. 유지할 대상을 명시해 변경 전후를 비교하고 원치 않은 영향을 찾습니다.

#### 04. 구현할 결과와 조건 고정

**그림의 윗부분이 벽 충돌을 늘리지 않는다.**

왜 이렇게 요청하나요? “그림의 윗부분이 벽 충돌을 늘리지 않는다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 지형은 그대로 두고 자연스러운 경계를 만듭니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 05. 관찰 가능한 기준으로 확인

**선택 테스트의 상태가 필수 과정과 구분된다.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 06. 사람 검사의 시작점 준비

**내가 조작해야 하는 부분은 실행할 화면과 시작 상태를 준비해 줘.**

왜 이렇게 요청하나요? 같은 기능이라도 시작 상태가 다르면 관찰 결과가 달라집니다. AI가 실행 화면과 재현 위치를 먼저 준비해야 사람이 이동·공격·소리·조작감을 같은 조건에서 확인할 수 있습니다.

#### 07. 사람이 실제로 본 것만 기록

**연결되지 않은 휴대폰의 터치나 사람이 보지 않은 재미·소리 품질을 대신 확인했다고 하지 마.**

왜 이렇게 요청하나요? AI가 준비한 검사와 사람이 직접 플레이하거나 들은 결과는 다른 근거입니다. 관찰하지 않은 조작감·소리·실기기 결과를 임의로 완료 처리하지 않게 합니다.

#### 08. 실제로 실행한 검사만 인정

**테스트 0개와 예전 소스 결과는 현재 성공으로 쓰지 마.**

## 이 작업에서 사용할 값과 규칙 전체

설계 시작값이며 측정된 성능·게임 성공 결과가 아닙니다. 구현은 AI가 수행합니다.

첫 규칙은 N=1, E=2, S=4, W=8을 조합하는 4비트, 16개 마스크다. 외곽과 안쪽을 어떻게 정의할지 먼저 정하고 각 마스크에 기본 타일을 할당한다. 대체 타일을 준비하고 누락을 로그로 남긴다. 3×3 반복, 16개 마스크 보드, 실제 랜덤 맵 순서로 확인한다.

Floor는 Ground층, 피해 예고는 Telegraph층, WallArt는 World층의 발 정렬을 사용한다. WallsCollision은 여전히 독립된 blocked 셀의 사각형이다. 수풀 그림을 추가했다고 이동 경로가 사라지지 않게 한다.

**선택 실습: 아이소메트릭 화면.** 디아블로처럼 비스듬한 격자 표현을 더 강하게 원한다면 완성본의 별도 ArtLab2D 사본에서만 Isometric Tilemap을 시험한다. 카메라만 기울이거나 타일 그림만 다이아몬드로 바꾸지 않는다. 논리 셀↔투영 좌표↔마우스 역변환, 벽 PolygonCollider2D, 발 정렬, 방향별 이동 속도와 공격 범위를 함께 검사한다. 본편 규격은 Rectangular 2D로 유지하며 선택 결과를 자동 병합하지 않는다. Unity는 Isometric Tilemap을 지원하지만, 게임 규칙의 좌표 변환은 별도 설계가 필요하다. [D01]
