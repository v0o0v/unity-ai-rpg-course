# 039. 다른 PC와 Android 에서 실행할 파일 만들기

**목표:** Editor 없이 실행할 배포물을 얻습니다.

**시작 상태:** 기본 완주 후보

## 한눈에 보는 기능의 흐름

릴리스 설정 → Windows 폴더 → Android APK → 깨끗한 실행 확인

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“다른 PC와 Android 에서 실행할 파일 만들기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 기본 완주 후보야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**현재 프로젝트의 실제 파일과 이미 결정한 규칙을 먼저 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 실제 사용 중인 코드에 연결

**이름이 다른 기존 구현이 있으면 새로 중복 제작하지 말고 그 구현에 연결해 줘.**

왜 이렇게 요청하나요? 예제와 이름이 다르더라도 현재 씬과 입력에서 호출하는 구현이 작업 대상입니다. 같은 기능을 새로 만들기보다 기존 진입점을 확인해 수정이 실제 게임에 반영되고 중복 실행되지 않게 합니다.

#### 03. 구현할 결과와 조건 고정

**Windows 와 Android 빌드를 만드는 프로젝트 전용 Editor 도구를 만들어 줘.**

왜 이렇게 요청하나요? “Windows 와 Android 빌드를 만드는 프로젝트 전용 Editor 도구를 만들어 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. Editor 없이 실행할 배포물을 얻습니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 04. 플랫폼별 실제 실행물 검사

**GameBuild.BuildWindows 와 GameBuild.BuildAndroidDevelopmentApk처럼 우리가 정의한 메서드를 실제로 등록하고 실행 경로를 확인해 줘.**

왜 이렇게 요청하나요? Editor Play와 배포 앱은 빌드·파일·실행 환경이 다릅니다. 설치 형식과 대상 플랫폼을 구분하고 각 실제 실행물에서 메뉴·입력·저장·콘텐츠를 다시 확인합니다.

#### 05. 구현할 결과와 조건 고정

**Unity 기본 명령이라고 가정하지 마.**

왜 이렇게 요청하나요? “Unity 기본 명령이라고 가정하지 마”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. Editor 없이 실행할 배포물을 얻습니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 06. 관찰 가능한 기준으로 확인

**빌드 전 검증과 BuildReport 실패를 실제 실패로 반환하게 해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 07. 플랫폼별 실제 실행물 검사

**Windows x86_64는 실행에 필요한 전체 폴더를, Android 는 IL2CPP ARM64 테스트 APK를 만들어 줘.**

왜 이렇게 요청하나요? Editor Play와 배포 앱은 빌드·파일·실행 환경이 다릅니다. 설치 형식과 대상 플랫폼을 구분하고 각 실제 실행물에서 메뉴·입력·저장·콘텐츠를 다시 확인합니다.

#### 08. 시작부터 플레이까지 한 흐름으로 연결

**출시 씬은 Boot·MainMenu·Town·Dungeon01이며 개발용 씬·치트·테스트 메뉴·민감한 로그·Pipeline 제어용 키나 서버는 Player에서 제외해 줘.**

왜 이렇게 요청하나요? 개발 씬을 직접 여는 것과 사용자가 타이틀에서 시작하는 것은 다른 경로입니다. 초기화·저장 선택·씬 이동·조작권을 연결해야 배포한 게임에서도 같은 기능을 사용할 수 있습니다.

#### 09. 플랫폼별 실제 실행물 검사

**서명 정보가 필요한 정식 APK/AAB는 내 서명 설정이 실제로 준비된 경우에만 만들어 줘.**

#### 10. 인증 정보 노출 방지

**비밀번호는 코드·명령 기록·로그에 넣지 마.**

왜 이렇게 요청하나요? 인증 정보가 프롬프트·로그·저장소에 남으면 다른 사람이 재사용할 수 있습니다. 로그인은 공식 경로에서 처리하고, AI에는 키 자체가 아니라 연결 성공 여부만 확인시킵니다.

#### 11. 플랫폼별 실제 실행물 검사

**서명 자료가 없으면 테스트 빌드와 정식 배포 준비를 구분해 줘.**

#### 13. 관찰 가능한 기준으로 확인

**실제 설치·실행 여부는 각각 확인하고 스토어 게시나 외부 업로드는 하지 마.**

#### 14. 구현과 실행은 AI에게 맡기기

**코드·설정·파일 생성·실행은 네가 맡고, 필요한 화면과 결과를 보여 줘.**

왜 이렇게 요청하나요? 설명이나 코드 조각만 받으면 실제 파일 생성·연결·실행이 빠질 수 있습니다. AI가 개발 작업까지 수행하고, 사람은 요구·승인·결과 판단을 맡도록 역할을 분명히 합니다.

## 왜 이렇게 만드는가

Windows 실행 파일만 떼어 보내지 않는다. 빌드가 만든 Data 폴더와 필요한 라이브러리를 포함한 전체 배포 폴더가 결과물이다. Android 로컬 테스트 APK와 스토어 제출용 AAB는 용도가 다르다. [S15][S16]

출시에는 개발용 원격 실행 기능을 포함하지 않는다. Pipeline의 런타임 서버·eval 접근 키·개발 치트·테스트 메뉴가 실제 빌드에서 빠졌는지 검사한다. 공식 Pipeline 안내도 이 도구를 로컬 개발용으로 설명한다. [S04]
