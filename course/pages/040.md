**목표:** 새 게임에서 보스 보상까지 완주합니다.

**시작 상태:** 기본 Windows·Android 배포물

## 한눈에 보는 기능의 흐름

새 게임 → 전투·전리품 → 저장 후 재실행 → 보스 보상

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“작은 RPG를 처음부터 끝까지 플레이하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 기본 Windows·Android 배포물야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**현재 프로젝트의 실제 파일과 이미 결정한 규칙을 먼저 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 실제 사용 중인 코드에 연결

**이름이 다른 기존 구현이 있으면 새로 중복 제작하지 말고 그 구현에 연결해 줘.**

왜 이렇게 요청하나요? 예제와 이름이 다르더라도 현재 씬과 입력에서 호출하는 구현이 작업 대상입니다. 같은 기능을 새로 만들기보다 기존 진입점을 확인해 수정이 실제 게임에 반영되고 중복 실행되지 않게 합니다.

#### 03. 현재 목표 밖의 기능을 추가하지 않기

**이제 새 기능을 늘리지 말고 완주 경로의 결함을 해결해 줘.**

왜 이렇게 요청하나요? AI가 관련 있어 보이는 기능을 한꺼번에 늘리면 무엇이 완료되어야 하는지 흐려집니다. 이번 목표와 직접 관계없는 구현을 제외해 현재 기능의 검증을 먼저 끝냅니다.

#### 04. 구현할 결과와 조건 고정

**실제 Windows/Android 결과물의 현재 버전과 소스 상태를 기록해 줘.**

왜 이렇게 요청하나요? “실제 Windows/Android 결과물의 현재 버전과 소스 상태를 기록해 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 새 게임에서 보스 보상까지 완주합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 05. 미확인을 완료와 분리

**새 게임부터 엔딩까지 아래 필수 흐름을 단계별 PASS/FAIL/BLOCKED/NOT RUN으로 평가해 줘.**

왜 이렇게 요청하나요? 만들어진 것, 검사에 실패한 것, 아직 확인하지 못한 것을 나눠야 다음 작업을 정확히 고를 수 있습니다. 실행할 조건이 없는 기능을 성공으로 기록하면 뒤에서 원인을 찾기 어려워집니다.

#### 06. 이동에 실패해도 아이템 보존

**특히 클릭/터치 입력, 피해 중복, 장비 옵션 불변, 가방 가득 참,**

왜 이렇게 요청하나요? 줍기·보관·장착은 한 물건의 위치를 바꾸는 작업입니다. 목적지 공간이 없거나 취소됐을 때 원래 위치를 먼저 지우지 않아야 아이템 분실과 복제를 막습니다.

#### 07. 전투 단계 전환을 한 번씩 처리

**저장 복원, 퀘스트 보상1회, 보스 패턴 회피, 사망 복귀, 앱 재개를 확인해 줘.**

왜 이렇게 요청하나요? 큰 피해·취소·사망으로 단계를 건너뛰거나 여러 조건이 함께 참이 되면 공격이 겹칠 수 있습니다. 진입·종료·보상을 분리해 끝난 단계의 예약이 남지 않도록 합니다.

#### 08. 구현할 결과와 조건 고정

**문제는 진행불가/데이터손실/조작오류/시각오류/개선요청으로 분류해 줘.**

왜 이렇게 요청하나요? “문제는 진행불가/데이터손실/조작오류/시각오류/개선요청으로 분류해 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 새 게임에서 보스 보상까지 완주합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 09. 증거·검사 상태·미실행의 적용 조건

**진행불가·데이터손실·필수 조작오류가 있으면 최종 PASS 를 주지 마.**

왜 이렇게 요청하나요? 증거는 어떤 대상에 어떤 검사를 실제 실행했는지 확인할 수 있는 자료입니다. PASS·FAIL·BLOCKED·NOT RUN은 성공·실패·조건 부족·미실행을 구분합니다. 스크린샷 하나는 멀티터치·저장 복구·전투 재미를 모두 입증하지 못합니다.

#### 10. 관찰 가능한 기준으로 확인

**실제 관측하지 않은 플랫폼이나 기기는 미검증으로 남겨 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 11. 종료 이후의 상태까지 확인

**고친 뒤 해당 재현과 핵심 회귀 검사를 다시 실행해 줘.**

왜 이렇게 요청하나요? 현재 화면에서 맞는 값도 저장하거나 다시 구성할 때 빠질 수 있습니다. 실제 종료·불러오기 전후에 ID·옵션·장착·진행을 비교해야 유지되는 범위를 확인할 수 있습니다.

#### 13. 종료 이후의 상태까지 확인

**실행 방법, 조작표, 저장 정책, 빌드 경로, 증거 위치를 써 줘.**

왜 이렇게 요청하나요? 현재 화면에서 맞는 값도 저장하거나 다시 구성할 때 빠질 수 있습니다. 실제 종료·불러오기 전후에 ID·옵션·장착·진행을 비교해야 유지되는 범위를 확인할 수 있습니다.

#### 14. 비교할 조건 고정

**개발 노력·코드량·테스트 숫자로 재미나 시각 완성도를 대신 평가하지 마.**

왜 이렇게 요청하나요? 여러 수치와 화면을 동시에 바꾸면 어떤 선택이 전투를 바꿨는지 알기 어렵습니다. 같은 조건에서 한 요소씩 조정하고 조작 실수·규칙 오류·주관적인 재미를 따로 관찰합니다.

#### 15. 관찰 가능한 기준으로 확인

**내가 실제 플레이하며 관찰한 검사와 네가 수행한 자동 검사를 명확히 분리해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 16. 구현과 실행은 AI에게 맡기기

**코드·설정·파일 생성·실행은 네가 맡고, 필요한 화면과 결과를 보여 줘.**

왜 이렇게 요청하나요? 설명이나 코드 조각만 받으면 실제 파일 생성·연결·실행이 빠질 수 있습니다. AI가 개발 작업까지 수행하고, 사람은 요구·승인·결과 판단을 맡도록 역할을 분명히 합니다.

#### 17. 막힌 준비를 먼저 해결

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

## 표시 기능을 스스로 정의해 보기

피격 숫자 표시 또는 상호작용 이름표 중 하나를 골라 켜기·끄기 옵션을 추가하세요. 처음 켰을 때, 껐을 때, 저장 후 재접속의 기대 결과를 먼저 자신의 말로 정합니다.

**확인할 결과:** 표시를 꺼도 실제 피해·상호작용은 유지됩니다. AI가 변경한 파일과 실제 관찰을 구분해 설명합니다.

## 왜 이렇게 만드는가

완성 판정은 ‘파일이 많다’나 ‘AI가 95점이라고 했다’가 아니다. 새 게임을 시작하고, 설명을 이해하고, 싸우고, 장비를 바꾸고, 저장하고, 보스를 이기는 경로가 실제로 연결되어야 한다.

처음 플레이하는 사람에게 조작을 미리 설명하지 않고 막힌 지점을 관찰한다. 재미와 불편함은 자동 테스트로만 판단할 수 없지만, 제기된 문제는 재현 가능한 수정 작업으로 바꿀 수 있다.
