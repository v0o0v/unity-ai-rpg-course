#### 02. 작업 대상부터 확인

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 공급자·어댑터·실제 호출의 적용 조건

**내 하네스의 공급자를 실제 Claude Code 호출로 확장해 줘.**

왜 이렇게 요청하나요? 공급자 어댑터는 하네스가 모델을 호출하고 응답을 읽는 연결부입니다. 고정 mock 응답과 실제 Claude 호출을 같은 결과 계약으로 연결할 수 있지만 검증 범위는 다릅니다. CLI 프로세스 종료 코드만으로 모델 요청 전체가 성공했다고 판단하지 않습니다. 응답 내부 오류도 봅니다.

#### 02. 비대화형 호출의 실제 지원 옵션

**설치본의 공식 도움말에서 비대화형 실행·구조화 출력·모델·권한·시간과 비용 제한을 먼저 확인해 줘.**

왜 이렇게 요청하나요? 여기서 비대화형은 게임 대사가 아니라 AI CLI를 한 번 호출하고 결과를 받는 방식입니다. 현재 클라이언트의 옵션과 응답 형식을 확인해야 지원되지 않는 인자를 추측해 실행하지 않습니다.

#### 03. 요청한 모델과 실제 실행 구분

**요청 모델은 claude-opus-5-5다.**

왜 이렇게 요청하나요? 모델 이름을 요청문에 적었다고 그 모델이 실제로 실행된 것은 아닙니다. 현재 계정·클라이언트가 지원하는지와 응답의 사용 정보를 확인해야 품질·비용 비교의 전제가 유지됩니다.

#### 04. 요청과 실제 권한을 구분

**실제 응답의 모델 정보와 오류·권한 거부·구조화 결과·사용량을 검사해 줘.**

왜 이렇게 요청하나요? 역할 프롬프트에 “이 파일만 수정”이라고 적는 것만으로 경로가 제한되지는 않습니다. 프로그램이 허용 경로와 요청 범위를 검사해 원본·비밀 파일·다른 담당 파일을 보호합니다.

#### 05. 구현할 결과와 조건 고정

**모델을 바꾸거나 안전 옵션을 우회해 성공시키지 마.**

왜 이렇게 요청하나요? “모델을 바꾸거나 안전 옵션을 우회해 성공시키지 마”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 역할별 실제 모델 응답을 받습니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 06. 설정과 실제 사용 결과 연결

**주 세션은 스킬로 도구를 운영하지만 격리된 역할은 명시한 자료를 읽고 변경안만 반환하게 해 줘.**

왜 이렇게 요청하나요? 데이터에 수치를 넣어도 사용 조건·UI·실제 전투가 그 값을 읽지 않으면 기능이 완성되지 않습니다. 선택 전후의 계산과 저장을 함께 확인합니다.

#### 07. 구현할 결과와 조건 고정

**Edit·셸·MCP·하위 위임 등의 권한은 역할에 자동 상속하지 마.**

왜 이렇게 요청하나요? “Edit·셸·MCP·하위 위임 등의 권한은 역할에 자동 상속하지 마”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 역할별 실제 모델 응답을 받습니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 08. 관찰 가능한 기준으로 확인

**현재 CLI에서 강제 가능한 설정을 확인하고 불가능한 경계는 설명해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 09. 인증 정보 노출 방지

**구독 로그인과 API 키 경로를 구분해 줘.**

왜 이렇게 요청하나요? 인증 정보가 프롬프트·로그·저장소에 남으면 다른 사람이 재사용할 수 있습니다. 로그인은 공식 경로에서 처리하고, AI에는 키 자체가 아니라 연결 성공 여부만 확인시킵니다.

#### 10. 인증 정보 노출 방지

**비밀키를 코드·프롬프트·로그에 쓰지 마.**

왜 이렇게 요청하나요? 인증 정보가 프롬프트·로그·저장소에 남으면 다른 사람이 재사용할 수 있습니다. 로그인은 공식 경로에서 처리하고, AI에는 키 자체가 아니라 연결 성공 여부만 확인시킵니다.

#### 11. 비용과 외부 작업은 별도 승인

**실제 호출 전 모델·최대 호출 수·예약 비용·시간 제한을 보여 주고 승인받아 줘.**

왜 이렇게 요청하나요? 로컬 파일을 고치는 것과 외부 서비스에 자료를 보내거나 비용을 지불하는 것은 영향이 다릅니다. 대상·내용·비용 범위를 확인한 승인 없이 요청이 확대되지 않도록 합니다.

#### 12. 관찰 가능한 기준으로 확인

**작은 한 역할 호출부터 실행해 실제 응답을 검사한 뒤 모의 공급자와 동일한 실행기 경로로 연결해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

왜 이렇게 요청하나요? 응답이 끊겨도 공급자에서 유료 작업이 수행됐을 수 있습니다. 사용량을 확인하기 전까지 비용 예약을 유지하고 다음 호출을 멈춰 한도를 우회하지 않게 합니다.

#### 14. 설정과 실제 사용 결과 연결

**현재 작성한 MyGameHarness를 확장하고 필요한 파일·테스트·스킬 연결을 직접 만들어 실행해 줘.**

왜 이렇게 요청하나요? 데이터에 수치를 넣어도 사용 조건·UI·실제 전투가 그 값을 읽지 않으면 기능이 완성되지 않습니다. 선택 전후의 계산과 저장을 함께 확인합니다.

먼저 확인 요청을 보내 AI가 검사와 화면을 준비하게 하세요. 그다음 아래 동작을 하나씩 확인합니다.

### AI에게 보낼 요구와 이유

#### 01. 검사할 입력과 관찰 지점 준비

**현재 구현한 “모의 응답 대신 실제 Claude 연결하기”의 자동 검사와 도구 결과 화면을 준비해 줘.**

#### 04. 비용 한도·예약·실사용량의 적용 조건

#### 06. 훅을 이벤트 보조 장치로 사용

#### 07. 사람 검사의 시작점 준비

**내가 조작해야 하는 부분은 실행할 화면과 시작 상태를 준비해 줘.**

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.
