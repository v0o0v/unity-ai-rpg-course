# 149. 상태와 보스 효과를 같은 데이터로 맞추기

**목표:** 예고·피격·해제가 정확히 표시됩니다.

**시작 상태:** 상태·룬·보스와 효과 역할

## 한눈에 보는 기능의 흐름

전투 상태 → 효과 시작 → 범위·시간 일치 → 상태 끝과 해제

**경계:** 취소된 보스 공격의 예고가 남지 않기

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“상태와 보스 효과를 같은 데이터로 맞추기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 상태·룬·보스와 효과 역할야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 관찰 가능한 기준으로 확인

**내가 만든 하네스의 실제 경로와 현재 게임 후보를 확인하고 game-feature로 이 작업을 처리해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 02. 구현과 판정의 책임 나누기

**필요한 담당 역할만 고르고 구현·QA·독립 검토를 분리해 줘.**

왜 이렇게 요청하나요? 구현자가 자신의 설명만으로 완료를 결정하면 놓친 가정을 그대로 통과시킬 수 있습니다. 원래 요구·실제 변경·테스트를 다른 관점에서 검토하고 쓰기 권한을 나눕니다.

#### 03. 작성한 도구를 실제로 사용

**변경안·승인한 후보·Unity 통합·현재 소스 검사를 실제로 연결하고, 참고 완성본으로 우회하지 마.**

왜 이렇게 요청하나요? 참고 완성본으로 몰래 실행하면 현재 만든 하네스의 누락이나 오류가 드러나지 않습니다. 실행 경로를 확인해 지금 개발한 도구가 작업과 검사를 수행하도록 합니다.

#### 04. 효과를 표현 계층에 연결

**신규 전투 기능을 기존 VFX 서비스에 연결해 줘.**

왜 이렇게 요청하나요? 피격·폭발·소멸은 게임 사건을 보여 주는 표현입니다. 효과가 사라지거나 반복 재생돼도 피해·보상 규칙이 달라지지 않도록 사건과 수명주기를 연결합니다.

#### 05. ID·고유 식별자·버전의 적용 조건

**eventId/shape/duration을 한 데이터로 받아 표시해 줘.**

왜 이렇게 요청하나요? ID는 어떤 대상이나 사건인지 구분하는 값입니다. 대상 종류마다 같은 ID를 어디까지 재사용할 수 있는지 규칙이 필요합니다. 이름·배열 위치·파일명은 항상 안정된 ID가 아닙니다. ID가 길거나 UUID라는 이유로 소유권 검사를 생략하지 않습니다.

#### 06. 피할 수 있는 정보와 실제 판정 일치

**피해 shape와 예고 shape를 별도 튜닝 값으로 복제하지 마.**

왜 이렇게 요청하나요? 표시한 위험 범위·시점과 실제 피해가 다르면 플레이어는 올바르게 반응해도 손해를 봅니다. 예고·판정·효과가 같은 규칙을 사용하게 해 공격을 학습할 수 있게 합니다.

#### 07. 종료 이후 남는 상태 방지

**중복 이벤트는 중복 재생하지 않고 취소·사망·풀 반환 시 효과 소유자를 정리해 줘.**

왜 이렇게 요청하나요? 기능을 켜는 것만큼 끝낼 때 입력·예약·효과를 정리하는 것도 중요합니다. 취소나 사망 같은 중간 종료에서도 이전 상태가 다음 행동으로 넘어가지 않게 합니다.

#### 08. 기존 결과를 보호

**Low 설정에서도 필수 위험 경계와 방향·타이밍을 보존해 줘.**

왜 이렇게 요청하나요? 새 작업이 이미 정상인 기능이나 자산까지 바꾸면 원인을 추적하기 어렵습니다. 유지할 대상을 명시해 변경 전후를 비교하고 원치 않은 영향을 찾습니다.

#### 09. 장착 결과를 원본에서 재계산

**효과에서 피해·룬 발동·퀘스트 보상을 다시 호출하지 마.**

왜 이렇게 요청하나요? 현재 능력치에 보너스를 계속 더하고 빼면 중복 이벤트나 저장 복원에서 오차가 쌓일 수 있습니다. 기본값과 현재 장착 상태에서 다시 계산해야 해제 후 원래 수치로 돌아옵니다.

#### 10. 아래 항목을 완료 조건으로 사용

**이 기능의 규칙:**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

#### 11. 상태 효과의 발생 원인과 수명 구분

**화상·냉기·표식·룬 발동·유물 선택·보스 단계에 효과를 붙인다.**

왜 이렇게 요청하나요? 지속 피해가 직접 공격용 효과를 다시 발생시키면 연쇄 피해나 무한 발동이 생길 수 있습니다. 피해 출처·적용 시간·중첩·해제 조건을 구분해 전투 조합이 의도한 횟수로 작동하게 합니다.

#### 12. 같은 요청의 반복 처리 정의

**효과 요청에는 eventId·원인 종류·대상·위치·범위·지속시간을 넣고, 같은 eventId의 중복 메시지는 중복 재생하지 않는다.**

왜 이렇게 요청하나요? 클릭 연타·재연결·중복 이벤트는 개발과 플레이 중 모두 발생할 수 있습니다. 반복돼도 한 번 처리해야 하는 결과와 매번 새로 처리할 결과를 나눠 데이터가 누적되지 않게 합니다.

#### 13. 스프라이트와 SpriteRenderer의 적용 조건

**발광이 큰 스프라이트를 만들어 실제 범위를 추측하게 하지 않는다.**

왜 이렇게 요청하나요? Sprite는 2D 그림에서 사용할 영역과 기준점을 나타내는 에셋이고, SpriteRenderer는 그것을 게임 세계에 그리는 컴포넌트입니다. PNG 전체와 화면의 캐릭터가 항상 같은 개념은 아닙니다. SpriteRenderer는 이동이나 체력을 자동으로 만들지 않습니다. 그림과 몸체는 분리합니다.

#### 14. 공격의 거리·시간을 명시

**공격 예고는 ‘디자인용 반경’과 ‘피해용 반경’을 따로 두지 않는다.**

왜 이렇게 요청하나요? 그림이 닿아 보이는 순간과 실제 판정 시간은 다를 수 있습니다. 사거리·각도·공격 간격·타격 시점을 고정하면 회피 가능한 구간과 실제 피해 결과를 같은 조건으로 검사할 수 있습니다.

#### 15. 구현할 결과와 조건 고정

**판정 shape에서 시각 데이터를 파생해 동일 크기로 배치한다.**

왜 이렇게 요청하나요? “판정 shape에서 시각 데이터를 파생해 동일 크기로 배치한다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 예고·피격·해제가 정확히 표시됩니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 16. 피할 수 있는 정보와 실제 판정 일치

**취소와 보스 사망이 오면 예고도 같은 사건 소유자로 정리한다.**

왜 이렇게 요청하나요? 표시한 위험 범위·시점과 실제 피해가 다르면 플레이어는 올바르게 반응해도 손해를 봅니다. 예고·판정·효과가 같은 규칙을 사용하게 해 공격을 학습할 수 있게 합니다.

#### 17. 효과를 표현 계층에 연결

**파티클이 끝날 때 피해를 주는 역방향 연결은 만들지 않는다.**

왜 이렇게 요청하나요? 피격·폭발·소멸은 게임 사건을 보여 주는 표현입니다. 효과가 사라지거나 반복 재생돼도 피해·보상 규칙이 달라지지 않도록 사건과 수명주기를 연결합니다.

#### 18. 구현할 결과와 조건 고정

**Low 효과 설정은 장식 입자·잔광·불필요한 bloom을 줄일 수 있지만 위험 경계·방향·타이밍은 남긴다.**

왜 이렇게 요청하나요? “Low 효과 설정은 장식 입자·잔광·불필요한 bloom을 줄일 수 있지만 위험 경계·방향·타이밍은 남긴다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 예고·피격·해제가 정확히 표시됩니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 19. 프레임 배열과 재생 규격 맞추기

**스프라이트 시트 효과와 셰이더는 이미 배운 구현을 활용하고, 이번 작업에서는 실제 전투 사건과 pooling lifecycle을 검증한다.**

왜 이렇게 요청하나요? 한 장에 그림이 여러 개 있어도 셀 크기·순서·여백이 일정하지 않으면 잘못 잘라 재생됩니다. 원본과 잘린 프레임을 대조해야 잘림·순서 뒤집힘·위치 튐을 찾을 수 있습니다.

왜 이렇게 요청하나요? 오류 수정 중 새 기능까지 넣으면 어떤 변경이 문제를 해결하거나 악화했는지 알기 어렵습니다. 원래 재현을 보존하고 작은 변경 뒤 같은 입력과 주변 정상 동작을 다시 확인합니다.

#### 05. 실패도 재현 자료로 보존

**실패 기록은 지우지 마.**

왜 이렇게 요청하나요? 실패한 입력과 로그가 있어야 같은 문제가 다시 생겼을 때 비교할 수 있습니다. 성공 기록으로 덮어쓰지 않고 전후 자료를 남기면 무엇을 고쳤는지 확인할 수 있습니다.

<summary>보낼 원문 전체 — 설명은 복사되지 않습니다</summary>

```text
풀 재사용 때 옛 대상과 색이 남는지 확인해 줘. 위험 표시를 끄는 최적화는 하지 마.
새 기능을 추가하지 말고 현재 오류와 실제 로그를 먼저 읽어 줘. 최소 수정 뒤 같은 재현과 관련 정상 동작을 다시 검사해 줘. 실패 기록은 지우지 마.
```

</details>

## 새 세션에서 이어가기

### AI에게 보낼 요구와 이유

#### 01. 이어서 할 작업 식별

**“상태와 보스 효과를 같은 데이터로 맞추기” 작업을 이어가고 싶어.**

왜 이렇게 요청하나요? 이름으로 재개할 작업을 찾고, 뒤에 이어지는 요청으로 실제 파일·진행 중 작업·기록을 다시 읽게 합니다. 제목만 보고 이전 상태를 기억한다고 가정하지 않습니다.

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

<summary>보낼 원문 전체 — 설명은 복사되지 않습니다</summary>

```text
“상태와 보스 효과를 같은 데이터로 맞추기” 작업을 이어가고 싶어. 실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘. 진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘. 기존 성공과 실패 기록은 보존해 줘.
```

</details>

## 왜 이렇게 만드는가

화상·냉기·표식·룬 발동·유물 선택·보스 단계에 효과를 붙인다. 효과 요청에는 eventId·원인 종류·대상·위치·범위·지속시간을 넣고, 같은 eventId의 중복 메시지는 중복 재생하지 않는다. 발광이 큰 스프라이트를 만들어 실제 범위를 추측하게 하지 않는다.

공격 예고는 ‘디자인용 반경’과 ‘피해용 반경’을 따로 두지 않는다. 판정 shape에서 시각 데이터를 파생해 동일 크기로 배치한다. 취소와 보스 사망이 오면 예고도 같은 사건 소유자로 정리한다. 파티클이 끝날 때 피해를 주는 역방향 연결은 만들지 않는다.
