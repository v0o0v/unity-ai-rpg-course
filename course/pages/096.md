## 1. 지금 상태 확인하기

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“3D 카메라 가림과 터치 조작 다듬기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 3D 환경과 모바일 입력야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**현재 프로젝트의 실제 파일과 이미 결정한 규칙을 먼저 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 실제 사용 중인 코드에 연결

**이름이 다른 기존 구현이 있으면 새로 중복 제작하지 말고 그 구현에 연결해 줘.**

왜 이렇게 요청하나요? 예제와 이름이 다르더라도 현재 씬과 입력에서 호출하는 구현이 작업 대상입니다. 같은 기능을 새로 만들기보다 기존 진입점을 확인해 수정이 실제 게임에 반영되고 중복 실행되지 않게 합니다.

#### 03. 카메라로 조작 정보 보존

**3D 카메라·가림·모바일 조작을 다듬어 줘.**

왜 이렇게 요청하나요? 카메라가 벽 안에 있거나 심하게 흔들리면 판정이 정상이어도 대상을 찾기 어렵습니다. 시야·선택·멀미 완화 설정을 확인해 화면 연출이 플레이를 방해하지 않게 합니다.

#### 04. 좌표계 혼동 방지

**입력은 카메라 수평 right/forward로 XZ에 변환하고 대각선 크기를 제한해 줘.**

왜 이렇게 요청하나요? 2D의 XY와 3D의 XZ는 같은 이동 의미라도 축 배치가 다릅니다. 변환 위치를 한 곳으로 모아야 지도·물리·카메라가 서로 다른 축을 높이나 전진 방향으로 해석하지 않습니다.

#### 05. 길찾기와 실제 도달을 구분

**가림 처리는 Renderer에만 적용하고 Collider/NavMesh/피해 LOS는 변경하지 마.**

왜 이렇게 요청하나요? 목적지 표시나 경로 목록이 있다고 캐릭터가 끝까지 갈 수 있는 것은 아닙니다. 이동 가능한 경로와 실제 몸체의 진행을 확인하고 막힌 지점을 성공으로 표시하지 않게 합니다.

#### 06. Material과 Shader의 적용 조건

**공유 Material 전역 변경과 원복 누수를 방지해 줘.**

왜 이렇게 요청하나요? Shader는 표면을 어떤 계산으로 그릴지 정하는 프로그램이고, Material은 그 계산에 넣을 색·텍스처·값을 모은 설정입니다. 같은 Shader로 여러 Material을 만들 수 있습니다. 3D용 Shader를 2D Renderer에서 그대로 쓴다고 같은 조명 반응이 보장되지는 않습니다.

#### 07. 시점과 화면 크기 기준 고정

**기본 사선 Orthographic를 유지하며 Android 에서 플레이어·예고·버튼이 읽히는지 확인해 줘.**

왜 이렇게 요청하나요? 카메라 방식이 바뀌면 같은 물체도 화면에서 보이는 크기와 겹침이 달라집니다. 시점을 먼저 정해 캐릭터 크기·선택·위험 표시를 같은 조건으로 맞춥니다.

#### 08. 동시 입력을 서로 독립적으로 유지

**UI 소비·멀티터치·화면 밖 포인터·Pause·씬 왕복을 실제 검사해 줘.**

왜 이렇게 요청하나요? 한 손가락을 떼었을 때 다른 손가락의 이동까지 해제되면 모바일 전투가 끊깁니다. 입력의 주체와 눌림 상태를 따로 관리하고 실제 두 손가락 조합으로 검사해야 합니다.

#### 09. 아래 항목을 완료 조건으로 사용

**적용할 세부 규칙:**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

#### 10. 시점과 화면 크기 기준 고정

**기본 카메라는 사선 Orthographic를 유지한다.**

왜 이렇게 요청하나요? 카메라 방식이 바뀌면 같은 물체도 화면에서 보이는 크기와 겹침이 달라집니다. 시점을 먼저 정해 캐릭터 크기·선택·위험 표시를 같은 조건으로 맞춥니다.

#### 11. Update·FixedUpdate·LateUpdate의 적용 조건

**추적은 LateUpdate에서 하고 이동 모터는 기존 주기로 동작한다.**

왜 이렇게 요청하나요? Update는 화면 프레임을 따라, FixedUpdate는 고정 시간 간격의 물리 갱신을 따라 호출됩니다. LateUpdate는 Update 이후의 후처리로 사용됩니다. 정확한 횟수는 프레임 상황과 설정에 따라 달라집니다. 카메라를 늦게 갱신한다고 모든 떨림이 해결되지는 않습니다. 보간·모터·실제 갱신 순서도 봅니다.

#### 12. 카메라·직교·원근의 적용 조건

**먼 적을 보기 위해 카메라를 무조건 멀리 빼면 Android 캐릭터가 너무 작아지므로 실제 화면의 몸체 크기·버튼 영역을 함께 본다.**

왜 이렇게 요청하나요? 카메라는 게임 세계를 어떤 위치·방향·범위로 볼지 정합니다. 직교 투영은 거리에 따른 크기 감소가 없고, 원근 투영은 먼 물체가 작아 보이게 합니다. 카메라를 멀리 옮기는 것만으로 직교 화면의 캐릭터 크기가 줄지는 않습니다. 직교 크기를 봅니다.

#### 13. Layer·LayerMask·Tag의 적용 조건

**가림 감지는 EnvironmentVisual 전용 레이어를 사용한다.**

왜 이렇게 요청하나요? Layer는 렌더링·물리 조회에서 대상을 분류하는 값이고 LayerMask는 어떤 레이어를 포함할지 고르는 필터입니다. Tag는 객체를 이름 있는 범주로 구분할 때 쓰며 역할이 다릅니다. Sorting Layer는 2D 그림 순서용입니다. 물리 Layer와 이름이 비슷하지만 자동 연동되지 않습니다.

#### 14. 길찾기와 실제 도달을 구분

**가까운 벽의 Renderer만 투명화/잘라내기 처리하고 Collider·NavMesh·피해 LOS는 유지한다.**

왜 이렇게 요청하나요? 목적지 표시나 경로 목록이 있다고 캐릭터가 끝까지 갈 수 있는 것은 아닙니다. 이동 가능한 경로와 실제 몸체의 진행을 확인하고 막힌 지점을 성공으로 표시하지 않게 합니다.

#### 15. Material과 Shader의 적용 조건

**공유 Material을 직접 바꿔 모든 벽이 투명해지지 않도록 개별 속성과 원복 수명을 관리한다.**

왜 이렇게 요청하나요? Shader는 표면을 어떤 계산으로 그릴지 정하는 프로그램이고, Material은 그 계산에 넣을 색·텍스처·값을 모은 설정입니다. 같은 Shader로 여러 Material을 만들 수 있습니다. 3D용 Shader를 2D Renderer에서 그대로 쓴다고 같은 조명 반응이 보장되지는 않습니다.

#### 16. UI 입력과 월드 입력 분리

**같은 포인터로 UI를 누른 뒤 배경을 공격하지 않게 UI 소비 규칙을 유지한다.**

왜 이렇게 요청하나요? 가방 버튼을 누른 입력이 뒤의 바닥 클릭으로도 처리되면 캐릭터가 원치 않게 이동하거나 공격합니다. 입력이 시작된 대상을 구분해 한 행동이 서로 다른 명령으로 중복 처리되지 않게 합니다.

#### 17. 관찰 가능한 기준으로 확인

**왼손 이동+오른손 공격, 손가락 화면 밖 이동, 앱 Pause에서 입력 상태를 검사한다.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 18. 구현과 실행은 AI에게 맡기기

**코드·설정·파일 생성·실행은 네가 맡고, 필요한 화면과 결과를 보여 줘.**

왜 이렇게 요청하나요? 설명이나 코드 조각만 받으면 실제 파일 생성·연결·실행이 빠질 수 있습니다. AI가 개발 작업까지 수행하고, 사람은 요구·승인·결과 판단을 맡도록 역할을 분명히 합니다.

#### 19. 막힌 준비를 먼저 해결

**수행하지 못한 작업과 필요한 승인·도구 연결은 구분해서 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

## 왜 이렇게 만드는가

3D에서는 위쪽으로 이동한다는 입력이 월드 +Z와 항상 같지 않다. 화면 기준 입력을 카메라의 수평 right/forward로 변환한 뒤 크기를1로 제한한다. 카메라가 고정이어도 이 변환을 명시하면 나중에 각도를 조절할 때 이동이 뒤집히지 않는다.

벽이 플레이어를 가릴 때 물리 Collider를 꺼 버리면 이동과 공격 규칙이 달라진다. 가림 처리는 외형에만 적용하고, 카메라↔캐릭터 사이의 어떤 부분을 줄일지 정한다.
