# 119. 막힌 작업을 안전하게 이어가기

**목표:** 실패를 지우지 않고 필요한 부분만 다시 합니다.

**시작 상태:** 공급자와 실행 기록

## 한눈에 보는 기능의 흐름

중단 기록 → 프로세스·비용 확인 → 미완료 작업 선택 → 제한된 재시도

![막힌 작업을 안전하게 이어가기 — 개념 설명용 구조](../lesson_visuals/119.svg)

**경계:** 끝난 작업과 결제를 중복 실행하지 않기

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“막힌 작업을 안전하게 이어가기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 공급자와 실행 기록야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 실패의 시간·비용 상한 두기

**실패·중단·재시도·예산 관리와 game-resume/game-fix 스킬을 만들어 줘.**

왜 이렇게 요청하나요? 실패를 자동으로 반복하면 같은 원인으로 비용과 시간이 계속 들 수 있습니다. 종료·사용량·확인 불가 상태를 기록하고 정한 한도에서 멈춘 뒤 원인을 판단하게 합니다.

#### 02. 기존 결과를 보호

**도구는 실제 프로세스·마지막 시도·원본 지문·승인·사용량을 읽고 이어갈 일을 결정해야 해.**

왜 이렇게 요청하나요? 새 작업이 이미 정상인 기능이나 자산까지 바꾸면 원인을 추적하기 어렵습니다. 유지할 대상을 명시해 변경 전후를 비교하고 원치 않은 영향을 찾습니다.

#### 03. 구현할 결과와 조건 고정

**일시 오류와 잘못된 입력·권한 부족·모델 오류를 나눠 줘.**

왜 이렇게 요청하나요? “일시 오류와 잘못된 입력·권한 부족·모델 오류를 나눠 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 실패를 지우지 않고 필요한 부분만 다시 합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 04. 실패의 시간·비용 상한 두기

**같은 입력의 일시 오류만 제한된 횟수로 재시도하고 권한·계획·소스 변경이 필요하면 새 버전의 작업으로 전환해 줘.**

왜 이렇게 요청하나요? 실패를 자동으로 반복하면 같은 원인으로 비용과 시간이 계속 들 수 있습니다. 종료·사용량·확인 불가 상태를 기록하고 정한 한도에서 멈춘 뒤 원인을 판단하게 합니다.

#### 05. 관찰 가능한 기준으로 확인

**외부 호출 전에 비용을 예약하고 응답 후 확인 가능한 사용량으로 정산해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 06. 기존 결과를 보호

**중단되어 사용량을 모르면 예약을 유지하고 다음 유료 호출을 자동 시작하지 마.**

#### 08. 실패도 재현 자료로 보존

**격리된 모의 실행에서 시간 초과·응답 손상·중간 중단·입력 변경을 시험하고 안전한 재개와 재개 거부를 각각 보여 줘.**

왜 이렇게 요청하나요? 실패를 자동으로 반복하면 같은 원인으로 비용과 시간이 계속 들 수 있습니다. 종료·사용량·확인 불가 상태를 기록하고 정한 한도에서 멈춘 뒤 원인을 판단하게 합니다.

#### 11. 설정과 실제 사용 결과 연결

**현재 작성한 MyGameHarness를 확장하고 필요한 파일·테스트·스킬 연결을 직접 만들어 실행해 줘.**

왜 이렇게 요청하나요? 데이터에 수치를 넣어도 사용 조건·UI·실제 전투가 그 값을 읽지 않으면 기능이 완성되지 않습니다. 선택 전후의 계산과 저장을 함께 확인합니다.

#### 12. 아래 항목을 완료 조건으로 사용

## 3. 결과를 직접 확인하기

### AI에게 보낼 요구와 이유

왜 이렇게 요청하나요? “이미 끝난 작업을 다시 결제하지 않는다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 실패를 지우지 않고 필요한 부분만 다시 합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 04. 공유 Editor의 작업 순서 보장

**실행 중 잠금을 제거하지 않는다.**

왜 이렇게 요청하나요? 씬 수정·Play·빌드가 같은 Editor에서 겹치면 서로의 상태를 바꿀 수 있습니다. 하나의 실행 창구와 잠금으로 순서를 만들되 사용자의 외부 편집까지 자동 차단한다고 가정하지 않습니다.

#### 05. 관찰 가능한 기준으로 확인

**실패 로그를 지우지 않는다.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 06. 훅을 이벤트 보조 장치로 사용

**사용자 중단 후 훅이 자동 재개하지 않는다.**

왜 이렇게 요청하나요? 실행 전과 실행 후 훅은 할 수 있는 일이 다릅니다. 상태 안내·검증 무효화·중복 방지와 같은 연결을 맡기되 훅 실행 자체를 테스트 성공이나 무제한 실행 권한으로 보지 않습니다.

#### 07. 사람 검사의 시작점 준비

**내가 조작해야 하는 부분은 실행할 화면과 시작 상태를 준비해 줘.**

왜 이렇게 요청하나요? 같은 기능이라도 시작 상태가 다르면 관찰 결과가 달라집니다. AI가 실행 화면과 재현 위치를 먼저 준비해야 사람이 이동·공격·소리·조작감을 같은 조건에서 확인할 수 있습니다.

#### 08. 사람이 실제로 본 것만 기록

**연결되지 않은 기기의 검사나 사람이 보지 않은 재미·소리 품질을 대신 확인했다고 하지 마.**

왜 이렇게 요청하나요? AI가 준비한 검사와 사람이 직접 플레이하거나 들은 결과는 다른 근거입니다. 관찰하지 않은 조작감·소리·실기기 결과를 임의로 완료 처리하지 않게 합니다.

#### 09. 실제로 실행한 검사만 인정

**테스트 0개와 예전 소스 결과는 현재 성공으로 쓰지 마.**

왜 이렇게 요청하나요? 실행된 검사가 없거나 같은 결과를 중복 집계한 경우는 기능을 확인한 것이 아닙니다. 실행 수와 개별 결과를 함께 확인해야 형식적인 성공 표시를 걸러낼 수 있습니다.

#### 02. 다음 작업이 읽을 인수인계

#### 03. 사람이 실제로 본 것만 기록

**자동 검사 결과와 내가 직접 확인한 결과를 구분하고, 내 관찰이 아직 없으면 미확인으로 남겨 줘.**

#### 05. 미확인을 완료와 분리

## 구체적인 예로 이해하기

### 재개는 재시작과 다르다

중단됐다고 이전 요청이 사라진 것은 아닙니다. 완료 여부가 불명확하면 조회부터 해야 합니다.

**시작 상태:** 응답을 받기 전에 프로그램이 중단된 작업 기록이 있습니다.

**직접 해 볼 동작:** 같은 run을 읽고 실행 중 프로세스·요청 ID·예산 예약·후보 상태를 확인하게 합니다.

**보여야 하는 결과:** 확인된 단계부터 재개하고 비용 미상·승인 대기는 그대로 표시합니다. 새 요청을 무작정 중복 제출하지 않습니다.

**이렇게 되면 아직 안 됩니다:** 실패한 run을 지워 남은 작업과 사용량을 초기화합니다.

**생각해 보기:** 오류를 없애려고 예산을 자동 두 배로 늘려도 될까요?

아닙니다. 한도는 실패할 때 무시하는 값이 아닙니다. 실패 원인을 좁히고 새 범위나 한도는 사용자가 판단합니다.

## 문제가 있으면

### AI에게 보낼 요구와 이유

#### 01. 같은 요청의 반복 처리 정의

**실행 여부가 불확실한 외부 작업을 즉시 반복하지 마.**

왜 이렇게 요청하나요? 클릭 연타·재연결·중복 이벤트는 개발과 플레이 중 모두 발생할 수 있습니다. 반복돼도 한 번 처리해야 하는 결과와 매번 새로 처리할 결과를 나눠 데이터가 누적되지 않게 합니다.

#### 02. 알 수 없는 비용을 무료로 취급하지 않기

**실제 결과를 먼저 조회하고 비용이 미상이면 예약을 유지해 확인을 요청해 줘.**

왜 이렇게 요청하나요? 응답이 끊겨도 공급자에서 유료 작업이 수행됐을 수 있습니다. 사용량을 확인하기 전까지 비용 예약을 유지하고 다음 호출을 멈춰 한도를 우회하지 않게 합니다.

#### 03. 원인 하나를 좁혀 수정

**새 기능을 추가하지 말고 현재 오류와 실제 로그를 먼저 읽어 줘.**

왜 이렇게 요청하나요? 오류 수정 중 새 기능까지 넣으면 어떤 변경이 문제를 해결하거나 악화했는지 알기 어렵습니다. 원래 재현을 보존하고 작은 변경 뒤 같은 입력과 주변 정상 동작을 다시 확인합니다.

#### 04. 원인 하나를 좁혀 수정

왜 이렇게 요청하나요? 오류 수정 중 새 기능까지 넣으면 어떤 변경이 문제를 해결하거나 악화했는지 알기 어렵습니다. 원래 재현을 보존하고 작은 변경 뒤 같은 입력과 주변 정상 동작을 다시 확인합니다.

#### 05. 실패도 재현 자료로 보존

**실패 기록은 지우지 마.**

왜 이렇게 요청하나요? 실패한 입력과 로그가 있어야 같은 문제가 다시 생겼을 때 비교할 수 있습니다. 성공 기록으로 덮어쓰지 않고 전후 자료를 남기면 무엇을 고쳤는지 확인할 수 있습니다.

## 새 세션에서 이어가기

### AI에게 보낼 요구와 이유

#### 01. 이어서 할 작업 식별

**“막힌 작업을 안전하게 이어가기” 작업을 이어가고 싶어.**

왜 이렇게 요청하나요? 이름으로 재개할 작업을 찾고, 뒤에 이어지는 요청으로 실제 파일·진행 중 작업·기록을 다시 읽게 합니다. 제목만 보고 이전 상태를 기억한다고 가정하지 않습니다.

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

```text
“막힌 작업을 안전하게 이어가기” 작업을 이어가고 싶어. 실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘. 진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘. 기존 성공과 실패 기록은 보존해 줘.
```

## 왜 이렇게 만드는가

재개는 처음부터 다시 실행하는 것과 다르다. 어떤 작업이 완료됐고 어떤 외부 호출이 아직 살아 있는지 확인한 뒤 필요한 단계만 수행한다. 진행 중인 프로세스가 있는데 잠금부터 지우면 중복 작업이 생긴다.

사용자는 “중단한 작업을 이어 줘”라고 말한다. AI는 상태·사건·원본 지문·비용을 조사하고 재개 가능한지 설명한다. 내용 수정이 필요한 실패는 기존 시도를 덮어쓰지 않고 새 수정 작업으로 만든다.
