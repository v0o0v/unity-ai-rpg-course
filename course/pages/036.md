# 036. 휴대폰에서 두 손가락으로 전투하기

**목표:** 이동하며 공격하고 앱 복귀 후 정상 조작합니다.

**시작 상태:** 기본 Android 실행 파일

## 한눈에 보는 기능의 흐름

이동 손가락 → 공격 손가락 → 각자 해제 → 앱 복귀 정리

![휴대폰에서 두 손가락으로 전투하기 — 개념 설명용 구조](../lesson_visuals/036.svg)

**경계:** 화면 밖에서 놓은 입력도 남기지 않기

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“휴대폰에서 두 손가락으로 전투하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 기본 Android 실행 파일야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**현재 프로젝트의 실제 파일과 이미 결정한 규칙을 먼저 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 실제 사용 중인 코드에 연결

**이름이 다른 기존 구현이 있으면 새로 중복 제작하지 말고 그 구현에 연결해 줘.**

왜 이렇게 요청하나요? 예제와 이름이 다르더라도 현재 씬과 입력에서 호출하는 구현이 작업 대상입니다. 같은 기능을 새로 만들기보다 기존 진입점을 확인해 수정이 실제 게임에 반영되고 중복 실행되지 않게 합니다.

#### 03. 구현할 결과와 조건 고정

**Android 가로 전용 UI와 생명주기를 실제 기기 기준으로 마무리해 줘.**

왜 이렇게 요청하나요? “Android 가로 전용 UI와 생명주기를 실제 기기 기준으로 마무리해 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 이동하며 공격하고 앱 복귀 후 정상 조작합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 04. 동시 입력을 서로 독립적으로 유지

**SafeArea 안에 HUD·조이스틱·버튼을 배치하고 양쪽 가로 회전을 지원해 줘.**

왜 이렇게 요청하나요? 한 손가락을 떼었을 때 다른 손가락의 이동까지 해제되면 모바일 전투가 끊깁니다. 입력의 주체와 눌림 상태를 따로 관리하고 실제 두 손가락 조합으로 검사해야 합니다.

#### 05. 구현할 결과와 조건 고정

**실제 터치 영역은 이미지보다 작지 않게 하고 주요 버튼 간 간격을 확보해 줘.**

왜 이렇게 요청하나요? “실제 터치 영역은 이미지보다 작지 않게 하고 주요 버튼 간 간격을 확보해 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 이동하며 공격하고 앱 복귀 후 정상 조작합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 06. 설정과 실제 사용 결과 연결

**초기 참고값은 공격168/스킬144/보조128 reference-unit이지만**

왜 이렇게 요청하나요? 데이터에 수치를 넣어도 사용 조건·UI·실제 전투가 그 값을 읽지 않으면 기능이 완성되지 않습니다. 선택 전후의 계산과 저장을 함께 확인합니다.

#### 07. 관찰 가능한 기준으로 확인

**화면 스케일 후 실제 크기를 검사하고 기기별 UI scale 옵션으로 조정해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 10. 종료 이후의 상태까지 확인

**검증된 현재 상태 저장을 요청해 줘.**

왜 이렇게 요청하나요? 현재 화면에서 맞는 값도 저장하거나 다시 구성할 때 빠질 수 있습니다. 실제 종료·불러오기 전후에 ID·옵션·장착·진행을 비교해야 유지되는 범위를 확인할 수 있습니다.

#### 11. 종료 이후의 상태까지 확인

**동시에 여러 저장을 실행하지 마.**

#### 12. 공유 Editor의 작업 순서 보장

**복귀 시 회전 공격 이동속도, 일시정지 상태, 오디오,UI 잠금을 정확히 복구해 줘.**

왜 이렇게 요청하나요? 씬 수정·Play·빌드가 같은 Editor에서 겹치면 서로의 상태를 바꿀 수 있습니다. 하나의 실행 창구와 잠금으로 순서를 만들되 사용자의 외부 편집까지 자동 차단한다고 가정하지 않습니다.

#### 13. 뒤로 가기의 화면 우선순위

**Android Back은 열린 상세창/인벤토리/대화창을 먼저 닫고 그다음 일시정지 메뉴를 열게 해 줘.**

왜 이렇게 요청하나요? 뒤로 가기 한 번에 여러 창이 닫히거나 게임이 즉시 종료되지 않도록 가장 위 화면부터 처리합니다. 다음 입력에서만 뒤의 메뉴로 이어지게 합니다.

#### 14. 상호작용·NPC·퀘스트의 적용 조건

**가방 선택은 hover 없이 가능해야 하고 아이템 근접 상호작용을 제공해 줘.**

왜 이렇게 요청하나요? 상호작용은 근처 객체와 대화·문 열기·줍기 등의 행동을 하는 기능입니다. NPC는 플레이어가 아닌 캐릭터, 퀘스트는 목표와 진행·보상 규칙을 가진 작업입니다. NPC의 말풍선을 봤다고 보상 지급이 완료된 것은 아닙니다. 데이터 상태와 저장을 확인합니다.

#### 15. 동시 입력을 서로 독립적으로 유지

#### 16. 관찰 가능한 기준으로 확인

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 17. 구현과 실행은 AI에게 맡기기

**코드·설정·파일 생성·실행은 네가 맡고, 필요한 화면과 결과를 보여 줘.**

왜 이렇게 요청하나요? 설명이나 코드 조각만 받으면 실제 파일 생성·연결·실행이 빠질 수 있습니다. AI가 개발 작업까지 수행하고, 사람은 요구·승인·결과 판단을 맡도록 역할을 분명히 합니다.

#### 18. 막힌 준비를 먼저 해결

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

<details>
<summary>보낼 원문 전체 — 설명은 복사되지 않습니다</summary>

```text
“휴대폰에서 두 손가락으로 전투하기” 작업을 이어가고 싶어. 실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘. 진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘. 기존 성공과 실패 기록은 보존해 줘.
```

</details>

## 왜 이렇게 만드는가

모바일 검증은 Game 창의 화면 비율만 바꾸는 것으로 끝나지 않는다. 손가락이 가리는 영역, 실제 터치 크기, 시스템 제스처, 홈 화면 이동, 발열과 기기 성능을 따로 확인한다.

기본 게임은 Landscape Left/Right 가로 방향만 지원한다. 세로 대응을 뒤늦게 조금 넣어 완성도를 흐리지 않는다. 출시 방향은 프로젝트 설정과 게임 UI에서 일관되어야 한다.
