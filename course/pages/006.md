# 006. 시작 메뉴와 테스트 공간 연결하기

**목표:** 시작 메뉴에서 전투를 만들 공간으로 들어갑니다.

**시작 상태:** 저장되는 2D 스프라이트

## 한눈에 보는 기능의 흐름

Boot → 시작 메뉴 → 테스트 공간 → 메뉴로 복귀

![시작 메뉴와 테스트 공간 연결하기 — 개념 설명용 구조](../lesson_visuals/006.svg)

**경계:** 초기화 서비스와 플레이어가 중복되지 않기

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“시작 메뉴와 테스트 공간 연결하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 저장되는 2D 스프라이트야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

### 직접 확인하기

1. AI가 읽은 실제 프로젝트 또는 도구 경로를 확인합니다.
2. 필수 준비가 없다면 문제 해결 요청을 보내고, 준비됐을 때 다음으로 갑니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**현재 프로젝트의 실제 파일과 이미 결정한 규칙을 먼저 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 실제 사용 중인 코드에 연결

**이름이 다른 기존 구현이 있으면 새로 중복 제작하지 말고 그 구현에 연결해 줘.**

왜 이렇게 요청하나요? 예제와 이름이 다르더라도 현재 씬과 입력에서 호출하는 구현이 작업 대상입니다. 같은 기능을 새로 만들기보다 기존 진입점을 확인해 수정이 실제 게임에 반영되고 중복 실행되지 않게 합니다.

#### 03. 지금 필요한 구조만 준비

**아래 폴더 구조로 최소 뼈대를 만들어 줘.**

왜 이렇게 요청하나요? 처음부터 전체 시스템을 한꺼번에 만들면 사용하지 않는 코드와 가정이 늘어납니다. 현재 기능의 자리·책임·범위를 먼저 만들고 실제 연결 여부를 단계별로 확인합니다.

#### 04. Play 모드·편집 모드·런타임의 적용 조건

**Assets/_Game 아래 Scripts/Core, Scripts/Runtime, Editor, Tests/EditMode,**

왜 이렇게 요청하나요? 편집 모드는 제작 상태이고 Play 모드는 게임 로직을 실행해 보는 상태입니다. 런타임은 게임이 실제로 실행되는 시간과 환경을 뜻합니다. Play에서 보인 상태만 보고 저장·재개방까지 통과했다고 기록하지 않습니다.

#### 05. 역할이 다른 파일의 위치 정리

**Tests/PlayMode, Data, Prefabs, Scenes, Materials, Art, Audio, UI를 만들어 줘.**

왜 이렇게 요청하나요? 테스트·정의 데이터·씬·프리팹·시각·소리·UI 파일을 목적별 폴더로 구분합니다. Audio라는 폴더 이름을 만들라는 요청이며, 아직 소리 믹싱이나 재생을 구현하는 단계는 아닙니다.

#### 06. MonoBehaviour와 컴포넌트 스크립트의 적용 조건

**Core는 가능한 Unity 의존 없는 계산·상태 모델, Runtime은 MonoBehaviour와 SO,**

왜 이렇게 요청하나요? MonoBehaviour는 Unity 객체의 컴포넌트로 동작하며 Update·OnEnable 같은 생명주기 기능에 참여하는 기반 클래스입니다. 모든 게임 계산이 이를 상속해야 하는 것은 아닙니다. 파일 이름이 맞아도 실제 GameObject에 붙고 필요한 참조가 연결됐는지 확인해야 합니다.

#### 07. 어셈블리 정의·asmdef·Editor 전용의 적용 조건

**Editor는 제작 도구로 구분하고 assembly definition의 참조를 실제 패키지 기준으로 연결해 줘.**

왜 이렇게 요청하나요? 어셈블리는 컴파일된 코드 묶음입니다. Unity의 asmdef는 코드 묶음의 참조·플랫폼·컴파일 범위를 정하는 데 사용합니다. Editor 도구와 게임 실행 코드는 분리해야 합니다. 폴더 이름을 바꿨다고 모든 참조 경계가 자동 수정되는 것은 아닙니다.

#### 08. 관찰 가능한 기준으로 확인

**Test assembly는 테스트 전용으로 설정하고 출시 런타임에서 NUnit/UnityEditor를 참조하지 않게 해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 09. 시작부터 플레이까지 한 흐름으로 연결

**Boot, MainMenu, Town, Dungeon01, TestArena 씬을 생성해 줘.**

왜 이렇게 요청하나요? 개발 씬을 직접 여는 것과 사용자가 타이틀에서 시작하는 것은 다른 경로입니다. 초기화·저장 선택·씬 이동·조작권을 연결해야 배포한 게임에서도 같은 기능을 사용할 수 있습니다.

#### 10. 씬과 씬 전환의 적용 조건

**지금은 MainMenu에 제목과 개발용 TestArena 진입 버튼만 있으면 된다.**

왜 이렇게 요청하나요? 씬은 오브젝트의 배치와 연결을 저장한 공간 단위입니다. 마을·던전·실습장을 다른 씬으로 나누거나, 한 씬 안에서 여러 구역을 관리할 수 있습니다. 씬 전환은 저장 파일 작성과 다릅니다. 영구 데이터는 별도 저장해야 합니다.

#### 11. 애플리케이션과 플레이 세션의 수명

**AppRoot와 GameSession의 최소 구조를 만들고 중복 초기화를 막아 줘.**

왜 이렇게 요청하나요? 앱 전체 서비스와 한 번의 플레이 상태를 나누면 씬 이동 때 같은 서비스를 여러 번 만들지 않을 수 있습니다. 생성 담당과 해제 시점을 정하고 최소 구조로 시작합니다.

#### 12. 지금 필요한 구조만 준비

**씬 안의 Player2D는 후속 작업에서 생성·연결할 자리만 준비해 줘.**

왜 이렇게 요청하나요? 처음부터 전체 시스템을 한꺼번에 만들면 사용하지 않는 코드와 가정이 늘어납니다. 현재 기능의 자리·책임·범위를 먼저 만들고 실제 연결 여부를 단계별로 확인합니다.

#### 13. 되돌아갈 원본 남기기

**기존 AutomationLab2D은 개발 테스트용으로 보존하되 출시 씬에 포함하지 마.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

#### 14. 어댑터·인터페이스·의존성 분리의 적용 조건

**모든 시스템을 빈 인터페이스 수십 개로 미리 만들지 마.**

왜 이렇게 요청하나요? 인터페이스는 기능에 요구하는 약속이고 어댑터는 서로 다른 구현을 그 약속에 맞춰 연결하는 구성요소입니다. 의존성 주입은 사용할 구현을 외부에서 지정하는 방식입니다. 모든 작은 함수를 인터페이스로 만들 필요는 없습니다. 실제 교체·검사 경계에 사용합니다.

#### 15. 시작부터 플레이까지 한 흐름으로 연결

**Boot→MainMenu→TestArena 전환과 TestArena 직접 실행의 초기화 횟수를 검증해 줘.**

왜 이렇게 요청하나요? 개발 씬을 직접 여는 것과 사용자가 타이틀에서 시작하는 것은 다른 경로입니다. 초기화·저장 선택·씬 이동·조작권을 연결해야 배포한 게임에서도 같은 기능을 사용할 수 있습니다.

#### 16. 구현과 실행은 AI에게 맡기기

**코드·설정·파일 생성·실행은 네가 맡고, 필요한 화면과 결과를 보여 줘.**

왜 이렇게 요청하나요? 설명이나 코드 조각만 받으면 실제 파일 생성·연결·실행이 빠질 수 있습니다. AI가 개발 작업까지 수행하고, 사람은 요구·승인·결과 판단을 맡도록 역할을 분명히 합니다.

#### 17. 막힌 준비를 먼저 해결

**수행하지 못한 작업과 필요한 승인·도구 연결은 구분해서 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 왜 이렇게 만드는가

모든 코드를 GameManager 한 파일에 넣는 방식은 처음에는 편하지만 나중에 장비 UI를 고치다가 전투가 깨지기 쉽다. 반대로 작은 게임에 복잡한 프레임워크를 잔뜩 넣을 필요도 없다.

이 작업은 계산 규칙, Unity에서 움직이는 코드, Editor용 제작 도구를 나눈다. 순수 계산 규칙은 EditMode 테스트로 확인하고, 실제 오브젝트·장면·입력은 PlayMode와 직접 플레이로 확인한다. 전역 객체 AppRoot는 한 개만 유지하며 씬 안의 플레이어 자체는 씬 전환 때 다시 만든다.
