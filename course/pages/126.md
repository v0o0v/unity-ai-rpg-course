# 126. 한 요청으로 필터 기능 끝내기

**목표:** 역할·검토·통합·검사를 실제로 거칩니다.

**시작 상태:** 전리품 확인 장면과 내가 만든 하네스

## 한눈에 보는 기능의 흐름

필터 요구 → 역할·검토 → 씬에 통합 → 실제 플레이 검사

**경계:** 규칙 함수만 만들고 UI 연결을 빠뜨리지 않기

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“한 요청으로 필터 기능 끝내기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 전리품 확인 장면과 내가 만든 하네스야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 표시와 아이템 존재 분리

**내가 만든 하네스의 실제 실행 경로와 game-feature 스킬로 전리품 필터를 완성해 줘.**

왜 이렇게 요청하나요? 이름표를 숨기는 기능이 아이템 자체를 끄거나 삭제하면 줍기·퀘스트·저장까지 달라집니다. 보기 편하게 하는 정책은 소유 데이터와 획득 기능을 바꾸지 않게 분리합니다.

#### 02. 구현할 결과와 조건 고정

**참고 완성본이나 별도의 우회 구현으로 처리하지 마.**

왜 이렇게 요청하나요? “참고 완성본이나 별도의 우회 구현으로 처리하지 마”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 역할·검토·통합·검사를 실제로 거칩니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

왜 이렇게 요청하나요? “LootPreviewLab2D에서 장비 이름표를 전체·마법 이상·희귀만 기준으로 보이게 해 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 역할·검토·통합·검사를 실제로 거칩니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 04. 표시와 아이템 존재 분리

**퀘스트·골드·재료·알 수 없는 종류와 등급은 항상 표시하고 전체 보기 중에는 필터보다 우선해 줘.**

왜 이렇게 요청하나요? 이름표를 숨기는 기능이 아이템 자체를 끄거나 삭제하면 줍기·퀘스트·저장까지 달라집니다. 보기 편하게 하는 정책은 소유 데이터와 획득 기능을 바꾸지 않게 분리합니다.

#### 05. 이동에 실패해도 아이템 보존

**이름표만 숨기고 드롭·Collider2D·줍기·아이템 ID·옵션·확률은 바꾸지 마.**

왜 이렇게 요청하나요? 줍기·보관·장착은 한 물건의 위치를 바꾸는 작업입니다. 목적지 공간이 없거나 취소됐을 때 원래 위치를 먼저 지우지 않아야 아이템 분실과 복제를 막습니다.

#### 06. 표시와 아이템 존재 분리

왜 이렇게 요청하나요? 구현자가 자신의 설명만으로 완료를 결정하면 놓친 가정을 그대로 통과시킬 수 있습니다. 원래 요구·실제 변경·테스트를 다른 관점에서 검토하고 쓰기 권한을 나눕니다.

#### 08. 관찰 가능한 기준으로 확인

**실제 역할·모의 역할·컴파일·자동 검사·내 조작 확인을 나눠 기록해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 09. 구현할 결과와 조건 고정

**아직 원래 던전 전체에 확장했다고 하지 말고 이 장면에서 실제 동작을 보여 줘.**

왜 이렇게 요청하나요? “아직 원래 던전 전체에 확장했다고 하지 말고 이 장면에서 실제 동작을 보여 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 역할·검토·통합·검사를 실제로 거칩니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 10. 설정과 실제 사용 결과 연결

**현재 작성한 MyGameHarness를 확장하고 필요한 파일·테스트·스킬 연결을 직접 만들어 실행해 줘.**

왜 이렇게 요청하나요? 데이터에 수치를 넣어도 사용 조건·UI·실제 전투가 그 값을 읽지 않으면 기능이 완성되지 않습니다. 선택 전후의 계산과 저장을 함께 확인합니다.

#### 11. 아래 항목을 완료 조건으로 사용

**정상 예와 실패 예를 실제로 보여 주고, 기존 기능이 유지되는지 확인해 줘.**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.
