# 125. 하네스로 작은 전리품 화면 만들기

**목표:** 별도 장면에서 세 등급 이름표를 봅니다.

**시작 상태:** 등록·검증한 unity_integrator 역할, 실제 게임 파일 연결, 올바른 후보의 Unity 명령 왕복

## 한눈에 보는 기능의 흐름

별도 확인 씬 → 세 등급 이름표 → 실제 줍기 → 기존 던전 재확인

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“하네스로 작은 전리품 화면 만들기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 Unity 통합과 검사 등록야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 구현할 결과와 조건 고정

**내 하네스로 기존 게임의 사본에 작은 LootPreviewLab2D 장면을 만들어 줘.**

왜 이렇게 요청하나요? “내 하네스로 기존 게임의 사본에 작은 LootPreviewLab2D 장면을 만들어 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 별도 장면에서 세 등급 이름표를 봅니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 02. 종료 이후의 상태까지 확인

**원래 마을·던전·저장은 유지해 줘.**

왜 이렇게 요청하나요? 현재 화면에서 맞는 값도 저장하거나 다시 구성할 때 빠질 수 있습니다. 실제 종료·불러오기 전후에 ID·옵션·장착·진행을 비교해야 유지되는 범위를 확인할 수 있습니다.

#### 03. 이동에 실패해도 아이템 보존

**일반·마법·희귀 장비 각각 하나와 이름표·실제 줍기 대상을 배치해 줘.**

왜 이렇게 요청하나요? 줍기·보관·장착은 한 물건의 위치를 바꾸는 작업입니다. 목적지 공간이 없거나 취소됐을 때 원래 위치를 먼저 지우지 않아야 아이템 분실과 복제를 막습니다.

#### 04. 상호작용·NPC·퀘스트의 적용 조건

**현재 게임의 아이템 인스턴스·드롭·상호작용 규칙을 쓰고 별도 모의 인벤토리로 바꾸지 마.**

왜 이렇게 요청하나요? 상호작용은 근처 객체와 대화·문 열기·줍기 등의 행동을 하는 기능입니다. NPC는 플레이어가 아닌 캐릭터, 퀘스트는 목표와 진행·보상 규칙을 가진 작업입니다. NPC의 말풍선을 봤다고 보상 지급이 완료된 것은 아닙니다. 데이터 상태와 저장을 확인합니다.

#### 05. 구현과 판정의 책임 나누기

**기획·구현·QA·Unity 통합·독립 검토 역할을 필요한 순서로 사용해 줘.**

왜 이렇게 요청하나요? 구현자가 자신의 설명만으로 완료를 결정하면 놓친 가정을 그대로 통과시킬 수 있습니다. 원래 요구·실제 변경·테스트를 다른 관점에서 검토하고 쓰기 권한을 나눕니다.

#### 06. 검토한 변경과 적용한 변경 일치

**C# 변경안과 Editor API 통합을 구분하고 승인한 후보에서만 장면을 생성해 줘.**

왜 이렇게 요청하나요? 승인 전에 본 내용과 실제 적용 내용이 달라지면 승인의 의미가 없어집니다. 후보와 기준 해시를 묶고 바뀐 경우 다시 검토하게 해 의도하지 않은 변경을 막습니다.

#### 07. 관찰 가능한 기준으로 확인

**컴파일·실제 EditMode 검사·Play 화면을 각각 확인해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 08. 반복해도 같은 결과 유지

**생성기를 두 번 실행해도 오브젝트가 중복되지 않게 해 줘.**

왜 이렇게 요청하나요? AI는 실패 복구 중 같은 생성 작업을 다시 실행할 수 있습니다. 새 오브젝트를 계속 추가하는 대신 자신이 만든 대상만 갱신해야 중복 렌더링·충돌·메모리 증가를 막습니다.

#### 09. 관찰 가능한 기준으로 확인

**세 아이템을 줍는 화면을 내가 확인할 수 있게 열어 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 10. 설정과 실제 사용 결과 연결

**현재 작성한 MyGameHarness를 확장하고 필요한 파일·테스트·스킬 연결을 직접 만들어 실행해 줘.**

왜 이렇게 요청하나요? 데이터에 수치를 넣어도 사용 조건·UI·실제 전투가 그 값을 읽지 않으면 기능이 완성되지 않습니다. 선택 전후의 계산과 저장을 함께 확인합니다.

#### 11. 아래 항목을 완료 조건으로 사용

**정상 예와 실패 예를 실제로 보여 주고, 기존 기능이 유지되는지 확인해 줘.**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

## 3. 결과를 직접 확인하기

먼저 확인 요청을 보내 AI가 검사와 화면을 준비하게 하세요. 그다음 아래 동작을 하나씩 확인합니다.

### AI에게 보낼 요구와 이유

#### 01. 검사할 입력과 관찰 지점 준비

**현재 구현한 “하네스로 작은 전리품 화면 만들기”의 자동 검사와 도구 결과 화면을 준비해 줘.**

왜 이렇게 요청하나요? 정상 예 하나만 보면 실패 조건을 놓치기 쉽습니다. 정상·경계·반례를 실제 입력으로 준비하고 사람이 볼 화면도 맞춰 확인 범위를 분명하게 합니다.

#### 02. 결과를 재확인할 근거 남기기

**정상 동작과 아래 실패 조건을 실제로 검사하고 대상·실행 수·결과를 보여 줘.**

왜 이렇게 요청하나요? “잘 됩니다”라는 요약만으로는 어떤 입력과 버전을 검사했는지 알 수 없습니다. 대상·실행 수·실패 내용·파일을 함께 남겨 같은 조건으로 다시 확인할 수 있게 합니다.

#### 03. 초기 실습장의 등급 표시 확인

**세 드롭 이름표에 일반·마법·희귀 등급이 표시된다.**

왜 이렇게 요청하나요? 지금은 세 종류 드롭을 배치하고 실제 줍기까지 연결하는 단계입니다. 필터 설정 변경은 다음 기능이며, 현재는 각 드롭의 등급이 올바르게 보이는지 확인합니다.

#### 04. 필터 이전의 실제 줍기 연결

**세 아이템을 하나씩 주우면 해당 이름표와 드롭만 사라지고 고유 ID가 가방에 한 번씩 남는다.**

왜 이렇게 요청하나요? 아직 이름표 숨김 기능을 요구하지 않습니다. 먼저 기존 게임의 소유권·드롭·줍기 경로가 실습장에서도 실제로 이어지는지 확인합니다.

#### 05. 되돌아갈 원본 남기기

**기존 게임 씬을 덮어쓰지 않는다.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

#### 06. 같은 요청의 반복 처리 정의

**씬 생성이 반복 가능하다.**

왜 이렇게 요청하나요? 클릭 연타·재연결·중복 이벤트는 개발과 플레이 중 모두 발생할 수 있습니다. 반복돼도 한 번 처리해야 하는 결과와 매번 새로 처리할 결과를 나눠 데이터가 누적되지 않게 합니다.

#### 07. 사람 검사의 시작점 준비

**내가 조작해야 하는 부분은 실행할 화면과 시작 상태를 준비해 줘.**

왜 이렇게 요청하나요? 같은 기능이라도 시작 상태가 다르면 관찰 결과가 달라집니다. AI가 실행 화면과 재현 위치를 먼저 준비해야 사람이 이동·공격·소리·조작감을 같은 조건에서 확인할 수 있습니다.

#### 08. 사람이 실제로 본 것만 기록

**연결되지 않은 기기의 검사나 사람이 보지 않은 재미·소리 품질을 대신 확인했다고 하지 마.**

왜 이렇게 요청하나요? AI가 준비한 검사와 사람이 직접 플레이하거나 들은 결과는 다른 근거입니다. 관찰하지 않은 조작감·소리·실기기 결과를 임의로 완료 처리하지 않게 합니다.

#### 09. 실제로 실행한 검사만 인정

**테스트 0개와 예전 소스 결과는 현재 성공으로 쓰지 마.**

### AI에게 보낼 요구와 이유

#### 01. API와 매개변수의 적용 조건

**씬 파일을 문자열로 고치지 말고 Editor API 로 연결해 줘.**

왜 이렇게 요청하나요? API는 프로그램이 다른 기능을 요청할 때 지켜야 하는 공개된 약속입니다. 기능 이름, 전달할 값, 반환값과 오류 조건이 포함됩니다. API가 있다는 말은 계정 권한·인터넷·비용 승인이 있다는 뜻이 아닙니다.

#### 02. 구현할 결과와 조건 고정

**코드만 만들고 장면 연결을 내게 맡기지 마.**

왜 이렇게 요청하나요? “코드만 만들고 장면 연결을 내게 맡기지 마”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 별도 장면에서 세 등급 이름표를 봅니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 01. 이어서 할 작업 식별

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

## 왜 이렇게 만드는가

여기서의 목표는 전체 게임을 다시 만드는 것이 아니라 기존 게임과 하네스의 연결을 확인하는 작은 실습장입니다. 세 종류의 드롭 이름표를 표시하고 실제 아이템을 하나씩 줍습니다. 표시를 바꾸는 전리품 필터는 다음 기능에서 추가합니다.

사용자가 C#·asmdef·Canvas·Inspector를 작성하지 않습니다. AI가 구현과 Editor 통합 도구를 생성하고 후보 프로젝트에서 실행합니다. 사용자는 기존 던전과 저장이 보존되는지, 실제 드롭의 ID가 가방으로 이동하는지 판단합니다.
