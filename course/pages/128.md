# 128. 내 도구를 대화로 운영하기

**목표:** 상태 조회·수정·재개를 명령 없이 합니다.

**시작 상태:** 내가 만든 스킬·훅·실행기

상태 물어보기 → 새 작업 요청 → 검증 요청 → 세션 재개

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“내 도구를 대화로 운영하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 내가 만든 스킬·훅·실행기야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 내 PC와 작업 세션 연결 확인

**내가 만든 하네스를 새 로컬 세션에서 대화로 운영할 수 있게 최종 연결해 줘.**

왜 이렇게 요청하나요? 웹 대화가 열린 것만으로 내 PC의 파일이나 Unity를 조작할 수 있는 것은 아닙니다. 실제 파일 읽기와 도구 호출의 결과로 어느 컴퓨터에서 작업하는지 확인합니다.

#### 02. 훅을 이벤트 보조 장치로 사용

**실제 실행기·게임 원본·후보·run·스킬·훅의 위치와 로드를 먼저 확인해 줘.**

왜 이렇게 요청하나요? 실행 전과 실행 후 훅은 할 수 있는 일이 다릅니다. 상태 안내·검증 무효화·중복 방지와 같은 연결을 맡기되 훅 실행 자체를 테스트 성공이나 무제한 실행 권한으로 보지 않습니다.

#### 03. AI 스킬과 SKILL.md의 적용 조건

**game-plan, game-feature, game-verify, game-fix, game-resume, game-status가 존재하는 기능만 실제로 호출하게 해 줘.**

왜 이렇게 요청하나요? AI 스킬은 반복 작업의 절차·참고 자료·도구 사용 방법을 묶은 정의입니다. 이 과정에서는 계획·구현·검사·수정·상태 조회를 자연어로 요청하는 입구로 사용합니다. 게임 안 공격 스킬과 AI 작업 스킬은 다른 의미입니다. 스킬 등록은 실제 계정·도구 연결을 대신하지 않습니다.

#### 04. 자연어를 실제 작업 절차에 연결

**스킬 파일이 있다는 사실과 실행 성공을 구분해 줘.**

왜 이렇게 요청하나요? 스킬 이름을 문서에 적은 것만으로 현재 AI 세션에서 사용할 수 있는 것은 아닙니다. 파일·로드·선택·실제 호출을 확인해 자연어 요청이 등록된 작업 절차로 이어지게 합니다.

#### 05. 관찰 가능한 기준으로 확인

**내가 고르는 작은 새 요구를 계획·구현·검토·후보·검사까지 처리하고, 격리된 실패 사본에서 수정과 재개를 보여 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 06. 비용과 외부 작업은 별도 승인

**유료 호출·외부 게시·검사 생략을 자동 승인하지 마.**

왜 이렇게 요청하나요? 로컬 파일을 고치는 것과 외부 서비스에 자료를 보내거나 비용을 지불하는 것은 영향이 다릅니다. 대상·내용·비용 범위를 확인한 승인 없이 요청이 확대되지 않도록 합니다.

#### 07. 관찰 가능한 기준으로 확인

**마지막에는 현재 할 수 있는 작업, 실제 통과한 검사, 아직 연결하지 못한 플랫폼과 기기, 다음 작업에서 읽을 기록을 보여 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 08. 기계가 읽을 값의 형식 검사

**내가 내부 명령이나 JSON을 직접 작성할 일이 없게 해 줘.**

왜 이렇게 요청하나요? 문자열이 JSON으로 읽힌다고 업무 규칙까지 올바른 것은 아닙니다. 필드·타입·범위·참조를 검사해 잘못된 값이 실제 코드·저장·편집기로 들어오지 않게 합니다.

#### 09. 설정과 실제 사용 결과 연결

**현재 작성한 MyGameHarness를 확장하고 필요한 파일·테스트·스킬 연결을 직접 만들어 실행해 줘.**

왜 이렇게 요청하나요? 데이터에 수치를 넣어도 사용 조건·UI·실제 전투가 그 값을 읽지 않으면 기능이 완성되지 않습니다. 선택 전후의 계산과 저장을 함께 확인합니다.

#### 10. 아래 항목을 완료 조건으로 사용

**정상 예와 실패 예를 실제로 보여 주고, 기존 기능이 유지되는지 확인해 줘.**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

## 3. 결과를 직접 확인하기

먼저 확인 요청을 보내 AI가 검사와 화면을 준비하게 하세요. 그다음 아래 동작을 하나씩 확인합니다.

### AI에게 보낼 요구와 이유

#### 01. 선택과 주민 반응 연결

**현재 구현한 “내 도구를 대화로 운영하기”의 자동 검사와 도구 결과 화면을 준비해 줘.**

왜 이렇게 요청하나요? 선택 버튼만 있어도 세계 상태가 바뀌지 않으면 이야기에 영향이 없습니다. 조건·결과·현재 퀘스트 상태를 대사와 연결하고 대화 중단·재방문 때도 일관되게 반응하도록 합니다.

#### 02. 결과를 재확인할 근거 남기기

**정상 동작과 아래 실패 조건을 실제로 검사하고 대상·실행 수·결과를 보여 줘.**

왜 이렇게 요청하나요? “잘 됩니다”라는 요약만으로는 어떤 입력과 버전을 검사했는지 알 수 없습니다. 대상·실행 수·실패 내용·파일을 함께 남겨 같은 조건으로 다시 확인할 수 있게 합니다.

#### 03. 구현할 결과와 조건 고정

**사용자 입력은 자연어와 승인·플레이 관찰뿐이다.**

왜 이렇게 요청하나요? “사용자 입력은 자연어와 승인·플레이 관찰뿐이다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 상태 조회·수정·재개를 명령 없이 합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 04. 자연어를 실제 작업 절차에 연결

**스킬은 실제 작성본을 호출한다.**

왜 이렇게 요청하나요? 스킬 이름을 문서에 적은 것만으로 현재 AI 세션에서 사용할 수 있는 것은 아닙니다. 파일·로드·선택·실제 호출을 확인해 자연어 요청이 등록된 작업 절차로 이어지게 합니다.

#### 05. 훅을 이벤트 보조 장치로 사용

**훅은 차단 상황을 무한 반복시키지 않는다.**

왜 이렇게 요청하나요? 실행 전과 실행 후 훅은 할 수 있는 일이 다릅니다. 상태 안내·검증 무효화·중복 방지와 같은 연결을 맡기되 훅 실행 자체를 테스트 성공이나 무제한 실행 권한으로 보지 않습니다.

#### 06. 미확인을 완료와 분리

**미실행 검사는 별도 남는다.**

왜 이렇게 요청하나요? 만들어진 것, 검사에 실패한 것, 아직 확인하지 못한 것을 나눠야 다음 작업을 정확히 고를 수 있습니다. 실행할 조건이 없는 기능을 성공으로 기록하면 뒤에서 원인을 찾기 어려워집니다.

#### 07. 사람 검사의 시작점 준비

**내가 조작해야 하는 부분은 실행할 화면과 시작 상태를 준비해 줘.**

왜 이렇게 요청하나요? 같은 기능이라도 시작 상태가 다르면 관찰 결과가 달라집니다. AI가 실행 화면과 재현 위치를 먼저 준비해야 사람이 이동·공격·소리·조작감을 같은 조건에서 확인할 수 있습니다.

#### 08. 사람이 실제로 본 것만 기록

**연결되지 않은 기기의 검사나 사람이 보지 않은 재미·소리 품질을 대신 확인했다고 하지 마.**

왜 이렇게 요청하나요? AI가 준비한 검사와 사람이 직접 플레이하거나 들은 결과는 다른 근거입니다. 관찰하지 않은 조작감·소리·실기기 결과를 임의로 완료 처리하지 않게 합니다.

#### 09. 실제로 실행한 검사만 인정

**테스트 0개와 예전 소스 결과는 현재 성공으로 쓰지 마.**

왜 이렇게 요청하나요? 실행된 검사가 없거나 같은 결과를 중복 집계한 경우는 기능을 확인한 것이 아닙니다. 실행 수와 개별 결과를 함께 확인해야 형식적인 성공 표시를 걸러낼 수 있습니다.

## 4. 결과를 남기고 마무리하기

실제로 본 결과를 아래 메모에 적고 AI에 전달합니다. 결과 저장 요청으로 현재 상태를 남긴 뒤 다음 페이지로 갑니다.

## 구체적인 예로 이해하기

### 말만 바뀌어도 같은 업무 경로로

스킬은 반복 업무를 찾아 실행하는 입구이고, 훅은 정해진 이벤트에 반응하는 보조 장치입니다. 둘 모두 실제 검사를 대신하지 않습니다.

**시작 상태:** 계획·구현·검증·수정·재개·상태 조회 스킬을 만들었습니다.

**직접 해 볼 동작:** “지금 어디까지 됐어?”와 “중단했던 필터 작업 이어가 줘”를 각각 보내 실제 다른 동작을 확인합니다.

**보여야 하는 결과:** 상태 조회는 변경 없이 기록만 읽고, 재개는 현재 프로세스·승인·소스를 확인한 뒤 남은 일을 수행합니다.

**이렇게 되면 아직 안 됩니다:** 조회만 했는데 유료 호출이나 게임 변경이 시작됩니다.

**생각해 보기:** 도구 실행 후 훅으로 이미 발생한 잘못된 변경을 사전 차단할 수 있나요?

## 문제가 있으면

### AI에게 보낼 요구와 이유

#### 01. 구현할 결과와 조건 고정

**현재 기록을 읽지 않고 기억으로 이어가지 마.**

왜 이렇게 요청하나요? “현재 기록을 읽지 않고 기억으로 이어가지 마”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 상태 조회·수정·재개를 명령 없이 합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 02. 구현과 판정의 책임 나누기

**실행기 경로·후보·권한·입력을 확인하고 독립된 검토와 실제 검사를 복원해 줘.**

왜 이렇게 요청하나요? 구현자가 자신의 설명만으로 완료를 결정하면 놓친 가정을 그대로 통과시킬 수 있습니다. 원래 요구·실제 변경·테스트를 다른 관점에서 검토하고 쓰기 권한을 나눕니다.

#### 03. 원인 하나를 좁혀 수정

**새 기능을 추가하지 말고 현재 오류와 실제 로그를 먼저 읽어 줘.**

왜 이렇게 요청하나요? 오류 수정 중 새 기능까지 넣으면 어떤 변경이 문제를 해결하거나 악화했는지 알기 어렵습니다. 원래 재현을 보존하고 작은 변경 뒤 같은 입력과 주변 정상 동작을 다시 확인합니다.

#### 04. 원인 하나를 좁혀 수정

**최소 수정 뒤 같은 재현과 관련 정상 동작을 다시 검사해 줘.**

왜 이렇게 요청하나요? 오류 수정 중 새 기능까지 넣으면 어떤 변경이 문제를 해결하거나 악화했는지 알기 어렵습니다. 원래 재현을 보존하고 작은 변경 뒤 같은 입력과 주변 정상 동작을 다시 확인합니다.

#### 05. 실패도 재현 자료로 보존

**실패 기록은 지우지 마.**

왜 이렇게 요청하나요? 실패한 입력과 로그가 있어야 같은 문제가 다시 생겼을 때 비교할 수 있습니다. 성공 기록으로 덮어쓰지 않고 전후 자료를 남기면 무엇을 고쳤는지 확인할 수 있습니다.

## 새 세션에서 이어가기

### AI에게 보낼 요구와 이유

#### 01. 이어서 할 작업 식별

**“내 도구를 대화로 운영하기” 작업을 이어가고 싶어.**

왜 이렇게 요청하나요? 이름으로 재개할 작업을 찾고, 뒤에 이어지는 요청으로 실제 파일·진행 중 작업·기록을 다시 읽게 합니다. 제목만 보고 이전 상태를 기억한다고 가정하지 않습니다.

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

## 나에게 필요한 검사 역할 만들기

번역 누락·퀘스트 참조·음원 출처 중 자신의 반복 작업 하나를 고르세요. 읽을 것, 보고할 것, 수정하면 안 되는 것, 실패 예제를 직접 정합니다. 코드와 스킬·테스트는 AI가 만듭니다.

**확인할 결과:** 정상 입력뿐 아니라 잘못된 입력과 권한 밖 수정이 실제로 거부됩니다. 상태 조회와 실행 요청이 구분됩니다.

## 왜 이렇게 만드는가

도구를 직접 만들었다는 것은 코드를 손으로 타이핑했다는 뜻이 아닙니다. 원하는 동작·권한·실패 조건을 정하고 실제 실행 결과를 이해하며, 새 요구에 맞게 바꿀 수 있다는 뜻입니다.
