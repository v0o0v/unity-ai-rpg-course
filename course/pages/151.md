# 151. 도감과 장비 비교로 새 기능 찾기

**목표:** 설명만으로 다음 행동을 선택합니다.

**시작 상태:** 대장간의 새 기능과 UI 역할

## 한눈에 보는 기능의 흐름

도감 발견 정보 → 장비 미리 비교 → 기능 안내 → 작은 화면 확인

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“도감과 장비 비교로 새 기능 찾기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 대장간의 새 기능과 UI 역할야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 관찰 가능한 기준으로 확인

**내가 만든 하네스의 실제 경로와 현재 게임 후보를 확인하고 game-feature로 이 작업을 처리해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 02. 구현과 판정의 책임 나누기

**필요한 담당 역할만 고르고 구현·QA·독립 검토를 분리해 줘.**

왜 이렇게 요청하나요? 구현자가 자신의 설명만으로 완료를 결정하면 놓친 가정을 그대로 통과시킬 수 있습니다. 원래 요구·실제 변경·테스트를 다른 관점에서 검토하고 쓰기 권한을 나눕니다.

#### 03. 작성한 도구를 실제로 사용

**변경안·승인한 후보·Unity 통합·현재 소스 검사를 실제로 연결하고, 참고 완성본으로 우회하지 마.**

왜 이렇게 요청하나요? 참고 완성본으로 몰래 실행하면 현재 만든 하네스의 누락이나 오류가 드러나지 않습니다. 실행 경로를 확인해 지금 개발한 도구가 작업과 검사를 수행하도록 합니다.

#### 04. 관찰 가능한 기준으로 확인

**새 기능의 발견형 도감·장비 비교·첫 확장 튜토리얼을 추가해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 05. 사용 성공과 자원 소비 묶기

**비교는 실제 능력치 계산기를 가상 상태에 적용하고 실제 장비·자원·쿨다운을 바꾸지 마.**

왜 이렇게 요청하나요? 실패한 사용에서 자원이 줄거나 연타로 여러 번 차감되면 표시와 실제 행동이 어긋납니다. 사용 조건·비용·대기시간을 함께 처리하고 실패 시 바뀌지 않아야 할 값을 확인합니다.

#### 06. 장착 결과를 원본에서 재계산

**룬 포함 여부와 일시 유물 제외 여부를 화면에 분명히 표시해 줘.**

왜 이렇게 요청하나요? 현재 능력치에 보너스를 계속 더하고 빼면 중복 이벤트나 저장 복원에서 오차가 쌓일 수 있습니다. 기본값과 현재 장착 상태에서 다시 계산해야 해제 후 원래 수치로 돌아옵니다.

#### 07. 상호작용·NPC·퀘스트의 적용 조건

**아직 보지 않은 유물 제안이나 퀘스트 답을 도감에 누출하지 마.**

왜 이렇게 요청하나요? 상호작용은 근처 객체와 대화·문 열기·줍기 등의 행동을 하는 기능입니다. NPC는 플레이어가 아닌 캐릭터, 퀘스트는 목표와 진행·보상 규칙을 가진 작업입니다. NPC의 말풍선을 봤다고 보상 지급이 완료된 것은 아닙니다. 데이터 상태와 저장을 확인합니다.

#### 08. 연출 전후의 실제 진행 유지

**튜토리얼은 건너뛰기·다시 보기를 지원하고 반복 보상을 주지 않게 해 줘.**

왜 이렇게 요청하나요? 영상이나 대사를 건너뛰어도 보상·다음 상태·조작권은 일관되게 처리되어야 합니다. 연출 재생 여부와 게임 진행을 분리해 엔딩·재개가 막히지 않게 합니다.

#### 11. 구현할 결과와 조건 고정

**기능이 많아지면 버튼이 있다는 사실만으로 찾기 어렵다.**

**숨겨진 퀘스트 정답이나 아직 선택하지 않은 다음 유물 제안을 보여 주지 않는다.**

**해금 도감은 영구 진행, 현재 검색과 탭은 UI 상태다.**

왜 이렇게 요청하나요? 영구 진행은 재실행 후에도 남는 데이터이고 탐험 세션은 이번 던전 동안만 유지할 상태입니다. 런타임 상태는 현재 살아 있는 객체·타이머·입력 등을 포함합니다. 하네스의 작업 run과 게임의 던전 run도 다른 개념입니다.

**원래 장비의 룬 제거와 새 장비 룬 적용을 함께 반영하고 실제 장착·재료 차감·쿨다운 변경은 하지 않는다.**

왜 이렇게 요청하나요? 스킬이나 장비를 바꾸는 기능을 이용해 대기시간·체력·마나를 반복 초기화하면 전투 규칙을 우회할 수 있습니다. 재계산할 능력과 유지할 현재 자원을 구분합니다.

#### 17. 상태 효과의 발생 원인과 수명 구분

**표식·유물 같은 임시 효과는 기본 비교에서 제외하되 포함 여부를 명시한다.**

왜 이렇게 요청하나요? 지속 피해가 직접 공격용 효과를 다시 발생시키면 연쇄 피해나 무한 발동이 생길 수 있습니다. 피해 출처·적용 시간·중첩·해제 조건을 구분해 전투 조합이 의도한 횟수로 작동하게 합니다.

#### 18. 거래·보상의 전체 성공 보장

**처음 구조한 대장장이가 필터→분해→제작→룬 순서의 짧은 안내를 제공한다.**

왜 이렇게 요청하나요? 재료 차감과 결과 지급이 따로 성공하면 손해나 복제가 생깁니다. 조건을 먼저 검사하고 한 거래로 반영하며 같은 요청을 다시 받아도 두 번 지급하지 않게 합니다.

#### 19. 다른 화면에서도 읽고 누를 수 있게

**한번에 긴 설명을 덮지 않고 현재 화면에서 다음 행동 한 개만 제시한다.**

왜 이렇게 요청하나요? 개발용 해상도에서 맞는 UI가 작은 기기나 긴 문장에서는 잘리거나 겹칠 수 있습니다. 텍스트 길이·버튼 영역·안전영역을 실제 배치로 검사합니다.

#### 02. 구현할 결과와 조건 고정

**공통 계산기의 임시 입력으로 결과만 보여 줘.**

왜 이렇게 요청하나요? “공통 계산기의 임시 입력으로 결과만 보여 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 설명만으로 다음 행동을 선택합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 03. 원인 하나를 좁혀 수정

**새 기능을 추가하지 말고 현재 오류와 실제 로그를 먼저 읽어 줘.**

왜 이렇게 요청하나요? 오류 수정 중 새 기능까지 넣으면 어떤 변경이 문제를 해결하거나 악화했는지 알기 어렵습니다. 원래 재현을 보존하고 작은 변경 뒤 같은 입력과 주변 정상 동작을 다시 확인합니다.

#### 05. 실패도 재현 자료로 보존

**실패 기록은 지우지 마.**

왜 이렇게 요청하나요? 실패한 입력과 로그가 있어야 같은 문제가 다시 생겼을 때 비교할 수 있습니다. 성공 기록으로 덮어쓰지 않고 전후 자료를 남기면 무엇을 고쳤는지 확인할 수 있습니다.

## 새 세션에서 이어가기

### AI에게 보낼 요구와 이유

#### 01. 이어서 할 작업 식별

**“도감과 장비 비교로 새 기능 찾기” 작업을 이어가고 싶어.**

왜 이렇게 요청하나요? 이름으로 재개할 작업을 찾고, 뒤에 이어지는 요청으로 실제 파일·진행 중 작업·기록을 다시 읽게 합니다. 제목만 보고 이전 상태를 기억한다고 가정하지 않습니다.

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

## 왜 이렇게 만드는가

기능이 많아지면 버튼이 있다는 사실만으로 찾기 어렵다. 확장 도감은 본인이 발견한 적 속성·재료·상태·룬·유물을 설명한다. 숨겨진 퀘스트 정답이나 아직 선택하지 않은 다음 유물 제안을 보여 주지 않는다. 해금 도감은 영구 진행, 현재 검색과 탭은 UI 상태다.

장비 비교는 현재 장비를 후보 장비로 바꾼 가상 상태에서 같은 능력치 계산기를 사용한다. 원래 장비의 룬 제거와 새 장비 룬 적용을 함께 반영하고 실제 장착·재료 차감·쿨다운 변경은 하지 않는다. 표식·유물 같은 임시 효과는 기본 비교에서 제외하되 포함 여부를 명시한다.
