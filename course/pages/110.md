# 110. 작업마다 필요한 자료만 준비하기

**목표:** 중단 후에도 같은 입력을 추적합니다.

**시작 상태:** 검증된 작업표와 상태 저장

## 한눈에 보는 기능의 흐름

작업과 입력 목록 → 실제 파일 묶음 → 입력 해시 → 재개 시 대조

**경계:** 필수 입력 없이 추측해서 실행하지 않기

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“작업마다 필요한 자료만 준비하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 검증된 작업표와 상태 저장야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 종료 이후의 상태까지 확인

**검증한 계획을 시작하는 실행 저장소와 역할별 입력 묶음을 만들어 줘.**

왜 이렇게 요청하나요? 현재 화면에서 맞는 값도 저장하거나 다시 구성할 때 빠질 수 있습니다. 실제 종료·불러오기 전후에 ID·옵션·장착·진행을 비교해야 유지되는 범위를 확인할 수 있습니다.

#### 02. 기존 결과를 보호

**실행마다 고유 run ID와 새 폴더를 만들고 원본·계획·역할 설정의 지문을 고정해 줘.**

왜 이렇게 요청하나요? 새 작업이 이미 정상인 기능이나 자산까지 바꾸면 원인을 추적하기 어렵습니다. 유지할 대상을 명시해 변경 전후를 비교하고 원치 않은 영향을 찾습니다.

#### 03. 작업표·완료 조건·계획의 적용 조건

**역할에게는 요구, 완료 조건, 명시한 읽기 파일, 필요한 선행 결과만 전달해 줘.**

왜 이렇게 요청하나요? 작업표는 목표·담당·입력·출력·선행 작업·완료 조건을 명시한 실행 계약입니다. 기획 AI가 초안을 만들 수 있지만 허용 경로·예산·실행 승인까지 마음대로 정하게 하지 않습니다. 계획이 JSON이라는 이유로 타당하거나 승인된 것은 아닙니다.

#### 04. 구현할 결과와 조건 고정

**누락된 파일과 너무 큰 입력은 조용히 생략하지 말고 작업 분할이나 재조사로 돌려 줘.**

왜 이렇게 요청하나요? “누락된 파일과 너무 큰 입력은 조용히 생략하지 말고 작업 분할이나 재조사로 돌려 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 중단 후에도 같은 입력을 추적합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 05. 구현할 결과와 조건 고정

**비밀 파일은 전달하지 마.**

왜 이렇게 요청하나요? “비밀 파일은 전달하지 마”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 중단 후에도 같은 입력을 추적합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 06. 기존 결과를 보호

**각 시도의 입력·응답·오류·시작과 종료를 별도 보존하고 끝난 기록을 덮어쓰지 마.**

왜 이렇게 요청하나요? 새 작업이 이미 정상인 기능이나 자산까지 바꾸면 원인을 추적하기 어렵습니다. 유지할 대상을 명시해 변경 전후를 비교하고 원치 않은 영향을 찾습니다.

#### 07. 관찰 가능한 기준으로 확인

**재개할 때 계획과 원본이 바뀌었는지 검사해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 08. 훅을 이벤트 보조 장치로 사용

**세션 시작 훅에는 실제 실행 상태의 위치와 재개 필요를 알려 주는 짧은 동작만 연결해 줘.**

왜 이렇게 요청하나요? 실행 전과 실행 후 훅은 할 수 있는 일이 다릅니다. 상태 안내·검증 무효화·중복 방지와 같은 연결을 맡기되 훅 실행 자체를 테스트 성공이나 무제한 실행 권한으로 보지 않습니다.

#### 09. 비용 한도·예약·실사용량의 적용 조건

**세션이 시작됐다는 이유로 유료 호출이나 Unity 빌드를 시작하지 마.**

왜 이렇게 요청하나요? 비용 한도는 허용한 지출 범위입니다. 예약은 호출 전에 잠재 사용량을 잡아 두는 것이고 실사용량은 응답·공급자 기록으로 확인합니다. 추정과 청구서는 다를 수 있습니다. 웹 구독료와 별도 API 요금·CDN 전송료가 같은 결제에 포함된다고 가정하지 않습니다.

#### 10. 같은 요청의 반복 처리 정의

**누락 입력·입력 변경·중복 run 경로·중단 후 조회를 실제로 시험해 줘.**

왜 이렇게 요청하나요? 클릭 연타·재연결·중복 이벤트는 개발과 플레이 중 모두 발생할 수 있습니다. 반복돼도 한 번 처리해야 하는 결과와 매번 새로 처리할 결과를 나눠 데이터가 누적되지 않게 합니다.

#### 11. 설정과 실제 사용 결과 연결

**현재 작성한 MyGameHarness를 확장하고 필요한 파일·테스트·스킬 연결을 직접 만들어 실행해 줘.**

왜 이렇게 요청하나요? 데이터에 수치를 넣어도 사용 조건·UI·실제 전투가 그 값을 읽지 않으면 기능이 완성되지 않습니다. 선택 전후의 계산과 저장을 함께 확인합니다.

#### 12. 아래 항목을 완료 조건으로 사용

**정상 예와 실패 예를 실제로 보여 주고, 기존 기능이 유지되는지 확인해 줘.**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

## 3. 결과를 직접 확인하기

먼저 확인 요청을 보내 AI가 검사와 화면을 준비하게 하세요. 그다음 아래 동작을 하나씩 확인합니다.

### AI에게 보낼 요구와 이유

#### 01. 검사할 입력과 관찰 지점 준비

**현재 구현한 “작업마다 필요한 자료만 준비하기”의 자동 검사와 도구 결과 화면을 준비해 줘.**

왜 이렇게 요청하나요? 정상 예 하나만 보면 실패 조건을 놓치기 쉽습니다. 정상·경계·반례를 실제 입력으로 준비하고 사람이 볼 화면도 맞춰 확인 범위를 분명하게 합니다.

#### 02. 결과를 재확인할 근거 남기기

**정상 동작과 아래 실패 조건을 실제로 검사하고 대상·실행 수·결과를 보여 줘.**

왜 이렇게 요청하나요? “잘 됩니다”라는 요약만으로는 어떤 입력과 버전을 검사했는지 알 수 없습니다. 대상·실행 수·실패 내용·파일을 함께 남겨 같은 조건으로 다시 확인할 수 있게 합니다.

## 왜 이렇게 만드는가

개발 총괄에게 필요한 모든 자료를 모든 역할에게 전부 보내면 비용과 혼동이 커진다. 각 작업은 필요한 원본과 선행 산출물만 받는다. 전달하지 않은 파일을 읽었다고 주장하면 안 된다.

SessionStart 훅은 지난 작업과 미검증 상태를 알려 주는 역할이다. 세션이 열렸다는 이유만으로 결제되는 모델 작업이나 Unity 빌드를 시작하지 않는다. 복구할 작업의 식별자와 상태를 확인한 뒤 자연어 요청을 기다린다.
