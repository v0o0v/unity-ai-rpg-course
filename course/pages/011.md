# 011. PC와 휴대폰에서 처음 실행하기

**목표:** Editor 밖에서 캐릭터를 움직입니다.

**시작 상태:** 이동 가능한 2D 프로젝트와 모바일 UI

## 한눈에 보는 기능의 흐름

하나의 프로젝트 → Windows 빌드 → Android 설치 → 각 기기 조작

**경계:** 빌드 성공과 실제 설치·조작 성공은 별개

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“PC와 휴대폰에서 처음 실행하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 이동 가능한 2D 프로젝트와 모바일 UI야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**현재 프로젝트의 실제 파일과 이미 결정한 규칙을 먼저 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 실제 사용 중인 코드에 연결

**이름이 다른 기존 구현이 있으면 새로 중복 제작하지 말고 그 구현에 연결해 줘.**

왜 이렇게 요청하나요? 예제와 이름이 다르더라도 현재 씬과 입력에서 호출하는 구현이 작업 대상입니다. 같은 기능을 새로 만들기보다 기존 진입점을 확인해 수정이 실제 게임에 반영되고 중복 실행되지 않게 합니다.

#### 03. 관찰 가능한 기준으로 확인

**현재 이동 테스트 공간을 Windows 와 Android 개발 빌드로 만들어 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 04. 설치된 도구에 맞추기

**실제 연결된 Editor로 빌드할 수 있는 명령인지 Docs/UNITY_COMMANDS.md와 --help를 확인해 줘.**

왜 이렇게 요청하나요? 버전마다 명령과 인자가 다를 수 있습니다. 기억에 의존해 명령을 조합하지 않고 현재 설치본의 도움말·패키지·실제 호출 결과를 기준으로 연결하게 합니다.

#### 05. 프로세스·종료 코드·표준 출력의 적용 조건

**별도 batchmode 프로세스를 쓰려면 같은 프로젝트를 열고 있는 Editor와 충돌하지 않게 해 줘.**

왜 이렇게 요청하나요? 프로세스는 실행 중인 프로그램입니다. PID는 프로세스 식별자, 종료 코드는 실행이 어떻게 끝났는지 나타내는 값입니다. stdout·stderr는 출력 통로지만 내용 의미까지 자동 보장하지는 않습니다. PC를 끄면 로컬 프로세스가 계속된다고 가정하지 않습니다. 실행 위치와 실제 상태를 확인합니다.

#### 06. 플랫폼별 실제 실행물 검사

**Windows x86_64 개발 빌드와 Android IL2CPP ARM64 테스트 APK를 분리해 줘.**

왜 이렇게 요청하나요? Editor Play와 배포 앱은 빌드·파일·실행 환경이 다릅니다. 설치 형식과 대상 플랫폼을 구분하고 각 실제 실행물에서 메뉴·입력·저장·콘텐츠를 다시 확인합니다.

#### 07. 시작부터 플레이까지 한 흐름으로 연결

**초기 씬은 Boot이며 메뉴에서 TestArena에 진입할 수 있어야 해.**

왜 이렇게 요청하나요? 개발 씬을 직접 여는 것과 사용자가 타이틀에서 시작하는 것은 다른 경로입니다. 초기화·저장 선택·씬 이동·조작권을 연결해야 배포한 게임에서도 같은 기능을 사용할 수 있습니다.

#### 08. 플랫폼별 빌드 산출물 분리

**Windows 는 Builds/WindowsDev, APK는 Builds/AndroidDev에 저장해 줘.**

왜 이렇게 요청하나요? Windows 실행 파일과 Android APK가 서로 덮어쓰지 않도록 출력 위치를 나눕니다. 어느 소스로 만든 어느 플랫폼의 파일인지 찾아 실제 실행할 수 있게 하기 위한 경로 지정입니다.

#### 09. 관찰 가능한 기준으로 확인

**빌드 보고서에 실제 경로, 종료 상태, 에러, 파일 크기, 사용 프로필을 남겨 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 10. 미확인을 완료와 분리

**연결된 Android 기기가 없거나 인증되지 않았으면 실기기 검증은 BLOCKED로 보고해 줘.**

왜 이렇게 요청하나요? 만들어진 것, 검사에 실패한 것, 아직 확인하지 못한 것을 나눠야 다음 작업을 정확히 고를 수 있습니다. 실행할 조건이 없는 기능을 성공으로 기록하면 뒤에서 원인을 찾기 어려워집니다.

#### 11. 빌드 생성과 실제 배포 실행 구분

**빌드만 성공한 것을 설치·플레이 성공으로 적지 마.**

왜 이렇게 요청하나요? 파일이 생성됐어도 필요한 폴더가 빠지거나 기기에서 실행되지 않을 수 있습니다. 배포물 전체를 실제 대상에서 열고 입력·저장까지 확인해야 빌드 환경과 게임 오류를 나눌 수 있습니다.

#### 12. 동시 입력을 서로 독립적으로 유지

**내가 확인할 PC 클릭/WASD, 모바일 두 손가락, 포커스 복귀 검사를 안내해 줘.**

왜 이렇게 요청하나요? 한 손가락을 떼었을 때 다른 손가락의 이동까지 해제되면 모바일 전투가 끊깁니다. 입력의 주체와 눌림 상태를 따로 관리하고 실제 두 손가락 조합으로 검사해야 합니다.

#### 13. 구현과 실행은 AI에게 맡기기

**코드·설정·파일 생성·실행은 네가 맡고, 필요한 화면과 결과를 보여 줘.**

왜 이렇게 요청하나요? 설명이나 코드 조각만 받으면 실제 파일 생성·연결·실행이 빠질 수 있습니다. AI가 개발 작업까지 수행하고, 사람은 요구·승인·결과 판단을 맡도록 역할을 분명히 합니다.

#### 14. 막힌 준비를 먼저 해결

**수행하지 못한 작업과 필요한 승인·도구 연결은 구분해서 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 3. 결과를 직접 확인하기

먼저 확인 요청을 보내 AI가 검사와 화면을 준비하게 하세요. 그다음 아래 동작을 하나씩 확인합니다.

### AI에게 보낼 요구와 이유

#### 01. 검사할 입력과 관찰 지점 준비

**방금 구현한 기능의 자동 검사와 확인 화면을 준비해 줘.**

왜 이렇게 요청하나요? 정상 예 하나만 보면 실패 조건을 놓치기 쉽습니다. 정상·경계·반례를 실제 입력으로 준비하고 사람이 볼 화면도 맞춰 확인 범위를 분명하게 합니다.

#### 02. 결과를 재확인할 근거 남기기

**정상 동작과 아래 실패 조건을 실제로 검사하고 대상·실행 수·결과를 보여 줘.**

## 왜 이렇게 만드는가

처음부터 플랫폼 빌드를 해 두면 나중에 완성 직전 ‘Editor에서만 되는 게임’이 되는 일을 피할 수 있다. 이 단계의 게임은 캐릭터가 움직이는 실습장뿐이어도 충분하다.

Unity 6의 Build Profiles에서 플랫폼별 설정을 관리한다. Android 테스트는 APK를 사용한다. AAB는 일반 APK처럼 휴대폰에서 눌러 바로 설치하는 결과물이 아니므로 이 단계에서는 만들지 않는다. [S15][S16]
