**목표:** 모든 기능이 함께 있을 때 병목을 줄입니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“확장 기능을 켠 휴대폰 성능 고치기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 보스·동료·정예·효과가 통합된 빌드야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 관찰 가능한 기준으로 확인

**내가 만든 하네스의 실제 경로와 현재 게임 후보를 확인하고 game-feature로 이 작업을 처리해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 02. 구현과 판정의 책임 나누기

**필요한 담당 역할만 고르고 구현·QA·독립 검토를 분리해 줘.**

왜 이렇게 요청하나요? 구현자가 자신의 설명만으로 완료를 결정하면 놓친 가정을 그대로 통과시킬 수 있습니다. 원래 요구·실제 변경·테스트를 다른 관점에서 검토하고 쓰기 권한을 나눕니다.

#### 03. 작성한 도구를 실제로 사용

**변경안·승인한 후보·Unity 통합·현재 소스 검사를 실제로 연결하고, 참고 완성본으로 우회하지 마.**

왜 이렇게 요청하나요? 참고 완성본으로 몰래 실행하면 현재 만든 하네스의 누락이나 오류가 드러나지 않습니다. 실행 경로를 확인해 지금 개발한 도구가 작업과 검사를 수행하도록 합니다.

#### 04. 구현할 결과와 조건 고정

**대장간 확장판의 실제 Android 병목을 측정한 뒤 한 가지씩 수정해 줘.**

왜 이렇게 요청하나요? “대장간 확장판의 실제 Android 병목을 측정한 뒤 한 가지씩 수정해 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 모든 기능이 함께 있을 때 병목을 줄입니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 05. 다른 이동 주체의 전환 관리

**기기·빌드·시드·콘텐츠·품질·동료/적 수를 고정하고 전후 데이터를 남겨 줘.**

왜 이렇게 요청하나요? 보조 캐릭터·탈것·수영 상태는 따라가기만 구현하면 길막·중복 생성·옛 입력 문제가 남을 수 있습니다. 제어권·추적 대상·진입과 종료 시 정리를 명확히 합니다.

#### 06. 피할 수 있는 정보와 실제 판정 일치

**경로·상태·이름표·VFX·아틀라스 중 관측된 원인만 수정하고 적이나 필수 예고를 꺼서 통과시키지 마.**

왜 이렇게 요청하나요? 표시한 위험 범위·시점과 실제 피해가 다르면 플레이어는 올바르게 반응해도 손해를 봅니다. 예고·판정·효과가 같은 규칙을 사용하게 해 공격을 학습할 수 있게 합니다.

#### 07. 끊긴 입력과 작업 정리

**던전10회와 앱 복귀 뒤 메모리·구독·동료 개체가 누적되는지 검사해 줘.**

왜 이렇게 요청하나요? 앱 전환이나 창 닫기에서는 정상적인 손 떼기 이벤트가 오지 않을 수 있습니다. 중단 시 눌림·예약·임시 효과를 정리해야 복귀 후 멋대로 움직이거나 공격하지 않습니다.

#### 08. 미확인을 완료와 분리

**Profiler 미연결 또는 기기 미확보는 추측 수치 대신 BLOCKED로 남겨 줘.**

왜 이렇게 요청하나요? 만들어진 것, 검사에 실패한 것, 아직 확인하지 못한 것을 나눠야 다음 작업을 정확히 고를 수 있습니다. 실행할 조건이 없는 기능을 성공으로 기록하면 뒤에서 원인을 찾기 어려워집니다.

#### 09. 아래 항목을 완료 조건으로 사용

**이 기능의 규칙:**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

#### 10. 전투 단계 전환을 한 번씩 처리

**상태 tick·정예 판단·동료 경로·새 VFX·이름표가 함께 켜진 실제 장면을 측정한다.**

왜 이렇게 요청하나요? 큰 피해·취소·사망으로 단계를 건너뛰거나 여러 조건이 함께 참이 되면 공격이 겹칠 수 있습니다. 진입·종료·보상을 분리해 끝난 단계의 예약이 남지 않도록 합니다.

#### 11. 지속 성능을 실기기로 확인

**목표 FPS는 지원 기기 기준으로 사람이 정하고 기기·해상도·품질·발열 상태·빌드 버전·콘텐츠 해시를 함께 기록한다.**

왜 이렇게 요청하나요? 앱을 막 켰을 때의 속도가 긴 플레이 동안 그대로 유지된다고 볼 수 없습니다. 장시간의 프레임 변화·메모리·중단 복귀를 실제 기기에서 확인해 목표 품질을 정합니다.

#### 12. 구현할 결과와 조건 고정

**60FPS라는 목표는 실측 결과가 아니다.**

왜 이렇게 요청하나요? “60FPS라는 목표는 실측 결과가 아니다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 모든 기능이 함께 있을 때 병목을 줄입니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 13. 다른 이동 주체의 전환 관리

**처음에는 동료와 적의 경로 요청을 프레임별로 분산하고 상태 컨테이너가 불필요한 매 프레임 할당을 만들지 않는지 본다.**

왜 이렇게 요청하나요? 보조 캐릭터·탈것·수영 상태는 따라가기만 구현하면 길막·중복 생성·옛 입력 문제가 남을 수 있습니다. 제어권·추적 대상·진입과 종료 시 정리를 명확히 합니다.

#### 14. FPS·프레임 시간·ms의 적용 조건

**모든 적을 꺼서 FPS를 올리는 최적화는 기능을 삭제한 것이다.**

왜 이렇게 요청하나요? FPS는 1초에 그린 프레임 수, 프레임 시간은 한 프레임에 걸린 시간입니다. 60FPS는 평균적으로 약 16.67ms, 30FPS는 약 33.33ms에 해당합니다. 순간 끊김은 평균만 보면 숨겨질 수 있습니다. 1000/FPS 계산은 시간 단위 관계입니다. 실제 성능을 측정한 숫자는 아닙니다.

#### 15. 피할 수 있는 정보와 실제 판정 일치

**Low 효과에서도 위험 예고·필수 UI는 유지한다.**

왜 이렇게 요청하나요? 표시한 위험 범위·시점과 실제 피해가 다르면 플레이어는 올바르게 반응해도 손해를 봅니다. 예고·판정·효과가 같은 규칙을 사용하게 해 공격을 학습할 수 있게 합니다.

#### 16. 같은 상황에서 병목 측정

**Unity는 실제 타깃 Development Build에 Profiler를 연결하는 절차를 제공한다.**

왜 이렇게 요청하나요? 느려 보인다는 느낌만으로 코드를 바꾸면 원인이 아닌 곳을 최적화할 수 있습니다. 같은 장면·기기·품질에서 프레임 구간과 작업 비용을 비교해 실제 병목을 찾습니다.

#### 17. 다른 이동 주체의 전환 관리

**측정 전후 같은 시드·장비·동료·적 구성·카메라 경로를 사용한다.**

왜 이렇게 요청하나요? 보조 캐릭터·탈것·수영 상태는 따라가기만 구현하면 길막·중복 생성·옛 입력 문제가 남을 수 있습니다. 제어권·추적 대상·진입과 종료 시 정리를 명확히 합니다.

#### 18. 반복 사용 뒤 자원 회수 확인

**평균만 보지 말고 긴 프레임, 초기 로딩, 던전 반복 입장 뒤 메모리 추세를 확인한다.**

왜 이렇게 요청하나요? 한 번 실행했을 때 정상이어도 반복 입장·생성·닫기에서 자원이 계속 남을 수 있습니다. 사용 전후와 반복 후를 비교해 의도한 캐시와 누수·과도한 할당을 구분합니다.

#### 19. 다른 이동 주체의 전환 관리

**씬 전환 뒤 남은 구독·효과·동료 인스턴스는 기능 오류이자 성능 문제일 수 있다.**

왜 이렇게 요청하나요? 보조 캐릭터·탈것·수영 상태는 따라가기만 구현하면 길막·중복 생성·옛 입력 문제가 남을 수 있습니다. 제어권·추적 대상·진입과 종료 시 정리를 명확히 합니다.

## 새 세션에서 이어가기

### AI에게 보낼 요구와 이유

#### 01. 이어서 할 작업 식별

**“확장 기능을 켠 휴대폰 성능 고치기” 작업을 이어가고 싶어.**

왜 이렇게 요청하나요? 이름으로 재개할 작업을 찾고, 뒤에 이어지는 요청으로 실제 파일·진행 중 작업·기록을 다시 읽게 합니다. 제목만 보고 이전 상태를 기억한다고 가정하지 않습니다.

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

```text
“확장 기능을 켠 휴대폰 성능 고치기” 작업을 이어가고 싶어. 실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘. 진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘. 기존 성공과 실패 기록은 보존해 줘.
```

## 왜 이렇게 만드는가

상태 tick·정예 판단·동료 경로·새 VFX·이름표가 함께 켜진 실제 장면을 측정한다. 목표 FPS는 지원 기기 기준으로 사람이 정하고 기기·해상도·품질·발열 상태·빌드 버전·콘텐츠 해시를 함께 기록한다. 60FPS라는 목표는 실측 결과가 아니다.

처음에는 동료와 적의 경로 요청을 프레임별로 분산하고 상태 컨테이너가 불필요한 매 프레임 할당을 만들지 않는지 본다. 모든 적을 꺼서 FPS를 올리는 최적화는 기능을 삭제한 것이다. Low 효과에서도 위험 예고·필수 UI는 유지한다. Unity는 실제 타깃 Development Build에 Profiler를 연결하는 절차를 제공한다. [P06]
