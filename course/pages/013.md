# 013. 적을 클릭해 접근하고 공격하기

**목표:** 벽 밖의 적에게 다가가 한 번씩 공격합니다.

**시작 상태:** 체력·피해 모델과 이동

## 한눈에 보는 기능의 흐름

적 선택 → 사거리까지 접근 → 방향·벽 검사 → 한 타격 적용

![적을 클릭해 접근하고 공격하기 — 개념 설명용 구조](../lesson_visuals/013.svg)

**경계:** 콜라이더가 여러 개여도 같은 타격은 한 번

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“적을 클릭해 접근하고 공격하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 체력·피해 모델과 이동야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**현재 프로젝트의 실제 파일과 이미 결정한 규칙을 먼저 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 실제 사용 중인 코드에 연결

**이름이 다른 기존 구현이 있으면 새로 중복 제작하지 말고 그 구현에 연결해 줘.**

왜 이렇게 요청하나요? 예제와 이름이 다르더라도 현재 씬과 입력에서 호출하는 구현이 작업 대상입니다. 같은 기능을 새로 만들기보다 기존 진입점을 확인해 수정이 실제 게임에 반영되고 중복 실행되지 않게 합니다.

#### 03. 좌표계 혼동 방지

**기본 공격을 Physics2D와 ActorRoot XY 좌표로 구현해 줘.**

왜 이렇게 요청하나요? 2D의 XY와 3D의 XZ는 같은 이동 의미라도 축 배치가 다릅니다. 변환 위치를 한 곳으로 모아야 지도·물리·카메라가 서로 다른 축을 높이나 전진 방향으로 해석하지 않습니다.

#### 04. 공격의 거리·시간을 명시

**반경1.8, 전방90도, 간격0.7초, 타격시점0.2초다.**

왜 이렇게 요청하나요? 그림이 닿아 보이는 순간과 실제 판정 시간은 다를 수 있습니다. 사거리·각도·공격 간격·타격 시점을 고정하면 회피 가능한 구간과 실제 피해 결과를 같은 조건으로 검사할 수 있습니다.

#### 05. 공격과 대상의 조합으로 중복 제거

**같은 attackSequenceId/actorId는 한 번만 피해를 줘.**

왜 이렇게 요청하나요? 한 공격이 여러 Hurtbox를 맞혀도 같은 적에게 한 번만 피해를 줍니다. 다음 공격은 다른 공격 ID이므로 다시 맞힐 수 있어야 합니다.

#### 06. 관찰 가능한 기준으로 확인

**OverlapCircle로 후보를 모으고 거리/내적/Environment Linecast/생존을 타격 시점에 확인해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 07. 공격의 거리·시간을 명시

**PC는 적 클릭→A* 접근→공격,Android 는 자동 접근 없이 전방선택 또는 헛스윙이다.**

왜 이렇게 요청하나요? 그림이 닿아 보이는 순간과 실제 판정 시간은 다를 수 있습니다. 사거리·각도·공격 간격·타격 시점을 고정하면 회피 가능한 구간과 실제 피해 결과를 같은 조건으로 검사할 수 있습니다.

#### 08. 충돌 위치와 피해 대상 구분

**자식 Hurtbox 두 개가 같은 Actor에 속하면 중복을 제거해 줘.**

왜 이렇게 요청하나요? 머리·몸통 충돌체가 각각 감지돼도 피해를 입는 적은 한 명입니다. 최종 Actor ID로 모아 같은 공격의 피해가 두 번 계산되지 않게 합니다.

#### 09. 그림의 동작과 게임 판정 분리

**피해 권한은 타이머 한 곳이고 Sprite 프레임과 Animation Event는 표시만 해 줘.**

왜 이렇게 요청하나요? 모델 동작이 이동이나 피해를 또 적용하면 기존 모터·전투 타이머와 충돌할 수 있습니다. 위치와 피해를 책임지는 주체를 하나로 두고 애니메이션은 정해진 사건을 표현하게 합니다.

#### 10. 보이는 장애물과 전투 판정 맞추기

**36→24, 벽뒤피해0, 두콜라이더도12피해, 중간사망/씬 전환 취소를 실제 검사해 줘.**

왜 이렇게 요청하나요? 거리만 맞으면 벽 뒤에도 피해가 들어가거나 빠른 투사체가 얇은 벽을 지나칠 수 있습니다. 사선과 이동 구간을 검사해 장애물의 의미가 전투에서도 유지되게 합니다.

#### 11. Collider와 몸체 경계의 적용 조건

**3D Collider나 Physics.OverlapSphere를 추가하지 마.**

왜 이렇게 요청하나요? Collider는 물리 검사에 사용하는 경계입니다. 보이는 그림과 같을 필요는 없습니다. 탑다운 캐릭터는 보통 발 주변에 작은 몸체 경계를 둡니다. 스프라이트를 크게 바꿨다고 몸체·사거리도 자동으로 키우지 않습니다.

#### 12. 아래 항목을 완료 조건으로 사용

**적용할 세부 규칙:**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

#### 13. 공격의 거리·시간을 명시

**기본 공격 간격0.7초, 타격시점0.2초, 반경1.8, 전방90도, 공격력12로 시작한다.**

왜 이렇게 요청하나요? 그림이 닿아 보이는 순간과 실제 판정 시간은 다를 수 있습니다. 사거리·각도·공격 간격·타격 시점을 고정하면 회피 가능한 구간과 실제 피해 결과를 같은 조건으로 검사할 수 있습니다.

#### 14. 구현할 결과와 조건 고정

**적 HP36이면 첫 타격 후24다.**

왜 이렇게 요청하나요? “적 HP36이면 첫 타격 후24다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 벽 밖의 적에게 다가가 한 번씩 공격합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 15. 좌표계 혼동 방지

**후보는 Physics2D.OverlapCircle 계열로 모으고 XY 거리·Facing과의 내적·Environment Linecast로 거른다.**

왜 이렇게 요청하나요? 2D의 XY와 3D의 XZ는 같은 이동 의미라도 축 배치가 다릅니다. 변환 위치를 한 곳으로 모아야 지도·물리·카메라가 서로 다른 축을 높이나 전진 방향으로 해석하지 않습니다.

#### 16. 앞뒤를 그리는 기준 정하기

**시각적 Sorting Layer 순서는 타격 여부를 결정하지 않는다.**

왜 이렇게 요청하나요? 2D 그림의 화면상 겹침 순서와 물리 충돌은 별개입니다. 바닥·배우·높은 장식의 정렬 기준을 나눠야 캐릭터가 기둥 앞뒤를 오갈 때 자연스럽게 가려집니다.

#### 17. 경로와 경유점의 적용 조건

**PC는 적을 클릭하면 유효 접근 waypoint를 선택해 사거리 안에서 공격한다.**

왜 이렇게 요청하나요? 경로는 목적지까지 지나갈 점이나 구간의 목록입니다. 이동 모터는 다음 경유점을 향해 움직이고, 새 입력·막힘·사망 때 경로를 취소하거나 갱신합니다. “도착”은 마지막 점과의 거리 기준·몸체 상태로 판단합니다. 정확히 같은 부동소수점 좌표가 되길 무한히 기다리지 않습니다.

#### 18. 구현할 결과와 조건 고정

**Android 는 자동 접근하지 않고 가까운 전방 적을 선택하거나 헛스윙한다.**

왜 이렇게 요청하나요? “Android 는 자동 접근하지 않고 가까운 전방 적을 선택하거나 헛스윙한다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 벽 밖의 적에게 다가가 한 번씩 공격합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 19. 관찰 가능한 기준으로 확인

**표적이 사망·사거리이탈·벽뒤로 이동하면 타격 시점에 다시 검증한다.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 20. ActorRoot·VisualRoot·ModelRoot의 적용 조건

**적 클릭은 ActorRoot뿐 아니라 자식 Hurtbox에서 소유 Actor ID를 찾는다.**

왜 이렇게 요청하나요? 이 이름들은 프로젝트에서 몸체·게임 규칙과 외형을 분리하기 위해 정한 오브젝트 이름입니다. ActorRoot는 실제 위치·생명·이동의 기준, VisualRoot나 ModelRoot는 그림·모델을 담는 하위 객체로 사용합니다. Root라는 이름만 붙인다고 이런 분리가 자동으로 생기지는 않습니다. 실제 컴포넌트와 호출 관계가 중요합니다.

#### 21. 프레임의 기준점 통일

**논리적으로 칼이 벽을 무시하지 않게 LOS는 발 기준의 2D 벽으로 검사한다.**

왜 이렇게 요청하나요? 걷기·공격 그림의 몸통 크기가 달라도 발은 같은 위치에 있어야 합니다. 기준점이 다르면 몸체는 정지해 있는데 그림만 튀거나 바닥을 미끄러지는 것처럼 보입니다.

#### 22. 구현할 결과와 조건 고정

**그림의 머리 위치에서 쏘는 3D ray를 사용하지 않는다.**

## 이 작업에서 사용할 값과 규칙 전체

설계 시작값이며 측정된 성능·게임 성공 결과가 아닙니다. 구현은 AI가 수행합니다.

기본 공격 간격0.7초, 타격시점0.2초, 반경1.8, 전방90도, 공격력12로 시작한다. 적 HP36이면 첫 타격 후24다. 후보는 Physics2D.OverlapCircle 계열로 모으고 XY 거리·Facing과의 내적·Environment Linecast로 거른다. 시각적 Sorting Layer 순서는 타격 여부를 결정하지 않는다.

PC는 적을 클릭하면 유효 접근 waypoint를 선택해 사거리 안에서 공격한다. Android 는 자동 접근하지 않고 가까운 전방 적을 선택하거나 헛스윙한다. 표적이 사망·사거리이탈·벽뒤로 이동하면 타격 시점에 다시 검증한다. 적 클릭은 ActorRoot뿐 아니라 자식 Hurtbox에서 소유 Actor ID를 찾는다.

논리적으로 칼이 벽을 무시하지 않게 LOS는 발 기준의 2D 벽으로 검사한다. 그림의 머리 위치에서 쏘는 3D ray를 사용하지 않는다. 피격 이펙트 위치는 별도의 표시점일 수 있다.

#### 02. 한 공격의 피해 중복 방지

## 새 세션에서 이어가기

### AI에게 보낼 요구와 이유

#### 01. 이어서 할 작업 식별

**“적을 클릭해 접근하고 공격하기” 작업을 이어가고 싶어.**

왜 이렇게 요청하나요? 이름으로 재개할 작업을 찾고, 뒤에 이어지는 요청으로 실제 파일·진행 중 작업·기록을 다시 읽게 합니다. 제목만 보고 이전 상태를 기억한다고 가정하지 않습니다.

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

## 왜 이렇게 만드는가

그림의 칼이 닿아 보이는지와 규칙상 타격 여부는 다를 수 있다. 여기서는 ActorRoot의 XY 발 좌표, Facing,AttackSnapshot을 정본으로 쓴다. 팔 이미지가 큰 방향으로 바뀌어도 사거리가 늘지 않는다.

피해는 공격 타이머 한 곳에서 확정한다. 스프라이트 프레임,Animation Event, 파티클이 각각 피해를 주면 한 번에 여러 번 맞는 오류가 된다. Physics2D 후보 조회에서 여러 Hurtbox가 반환돼도 같은 Actor ID는 한 번만 처리한다.
