# 087. 같은 캐릭터를 실제 3D 모델로 만들기

**목표:** 원래 캐릭터의 특징을 가진 모델을 사용합니다.

**시작 상태:** 3D 이동 몸체

## 한눈에 보는 기능의 흐름

캐릭터 특징 → 3D 실루엣 → 플레이어·적 모델 → 작은 화면 비교

**경계:** 큰 무기 외형이 사거리를 늘리지 않기

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“같은 캐릭터를 실제 3D 모델로 만들기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 3D 이동 몸체야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**현재 프로젝트의 실제 파일과 이미 결정한 규칙을 먼저 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 실제 사용 중인 코드에 연결

**이름이 다른 기존 구현이 있으면 새로 중복 제작하지 말고 그 구현에 연결해 줘.**

왜 이렇게 요청하나요? 예제와 이름이 다르더라도 현재 씬과 입력에서 호출하는 구현이 작업 대상입니다. 같은 기능을 새로 만들기보다 기존 진입점을 확인해 수정이 실제 게임에 반영되고 중복 실행되지 않게 합니다.

#### 03. 구현할 결과와 조건 고정

**같은 모험가, 적 세 종류, 보스를 실제 3D 메시로 만들어 줘.**

왜 이렇게 요청하나요? “같은 모험가, 적 세 종류, 보스를 실제 3D 메시로 만들어 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 원래 캐릭터의 특징을 가진 모델을 사용합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 04. 서로 다른 자산의 정체성 유지

**2D 팔레트와 실루엣 특징을 유지하고, 기본 경로는 Unity Editor의 단순 메시와 도형 조합으로 해 줘.**

왜 이렇게 요청하나요? 프레임·방향·모델마다 무기 손이나 장비 형태가 달라지면 같은 캐릭터로 읽히지 않습니다. 기준을 먼저 고정하고 실제 작은 화면에서 나란히 비교해 채택할 결과를 고릅니다.

#### 05. 프레임의 기준점 통일

**ModelRoot, 발 기준점, WeaponSocket을 분리하고 ActorRoot, 피해 범위, 이동 반경은 바꾸지 마.**

왜 이렇게 요청하나요? 걷기·공격 그림의 몸통 크기가 달라도 발은 같은 위치에 있어야 합니다. 기준점이 다르면 몸체는 정지해 있는데 그림만 튀거나 바닥을 미끄러지는 것처럼 보입니다.

#### 06. 스프라이트와 SpriteRenderer의 적용 조건

**캐릭터를 Sprite 빌보드만으로 대체한 뒤 3D 모델을 완성했다고 하지 마.**

왜 이렇게 요청하나요? Sprite는 2D 그림에서 사용할 영역과 기준점을 나타내는 에셋이고, SpriteRenderer는 그것을 게임 세계에 그리는 컴포넌트입니다. PNG 전체와 화면의 캐릭터가 항상 같은 개념은 아닙니다. SpriteRenderer는 이동이나 체력을 자동으로 만들지 않습니다. 그림과 몸체는 분리합니다.

#### 07. 같은 요청의 반복 처리 정의

**떠 있는 부품, 뒤집힌 면, 재질 중복과 실제 화면에서의 식별성을 확인해 줘.**

왜 이렇게 요청하나요? 클릭 연타·재연결·중복 이벤트는 개발과 플레이 중 모두 발생할 수 있습니다. 반복돼도 한 번 처리해야 하는 결과와 매번 새로 처리할 결과를 나눠 데이터가 누적되지 않게 합니다.

#### 08. 비용과 외부 작업은 별도 승인

**외부 서비스나 유료 에셋은 승인 없이 구매하지 마.**

왜 이렇게 요청하나요? 로컬 파일을 고치는 것과 외부 서비스에 자료를 보내거나 비용을 지불하는 것은 영향이 다릅니다. 대상·내용·비용 범위를 확인한 승인 없이 요청이 확대되지 않도록 합니다.

#### 09. 아래 항목을 완료 조건으로 사용

**적용할 세부 규칙:**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

#### 10. 기존 결과를 보호

**플레이어는 높이 1.8, 짧은 붉은 망토, 회색 갑옷, 오른손 검을 유지한다.**

왜 이렇게 요청하나요? 새 작업이 이미 정상인 기능이나 자산까지 바꾸면 원인을 추적하기 어렵습니다. 유지할 대상을 명시해 변경 전후를 비교하고 원치 않은 영향을 찾습니다.

#### 11. 구현할 결과와 조건 고정

**근접병은 방패, 석궁수는 가벼운 몸과 석궁, 거구는 큰 어깨, 보스는 머리 장식으로 구분한다.**

왜 이렇게 요청하나요? “근접병은 방패, 석궁수는 가벼운 몸과 석궁, 거구는 큰 어깨, 보스는 머리 장식으로 구분한다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 원래 캐릭터의 특징을 가진 모델을 사용합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 12. 구현할 결과와 조건 고정

**같은 재질 세트를 활용해 캐릭터와 지역의 화풍을 통일한다.**

왜 이렇게 요청하나요? “같은 재질 세트를 활용해 캐릭터와 지역의 화풍을 통일한다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 원래 캐릭터의 특징을 가진 모델을 사용합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 13. 프레임의 순서와 시간 맞추기

**ActorRoot에는 이동·체력·전투를 두고 ModelRoot에 메시와 애니메이션용 관절을 둔다.**

왜 이렇게 요청하나요? 이미지나 동작 파일이 있어도 순서·속도·전환 기준이 맞지 않으면 끊기거나 타격 시점과 어긋납니다. 실제 사용 크기와 반복 재생에서 연결이 자연스러운지 확인합니다.

#### 14. Hitbox·Hurtbox·Body의 적용 조건

**모델을 크게 만들었다고 Body 반경과 AttackRange를 늘리지 않는다.**

왜 이렇게 요청하나요? Hitbox는 공격이 맞는 범위, Hurtbox는 피해를 받을 수 있는 대상 범위, Body는 이동을 막는 몸체 범위를 뜻하는 설계 용어입니다. 같은 Collider로 합칠 수도 있지만 목적은 다릅니다. 시각 효과의 큰 불꽃 전체를 실제 공격 범위로 간주하지 않습니다. 예고·판정·효과의 관계를 명시합니다.

#### 15. 구현할 결과와 조건 고정

**큰 거구에 원래 별도의 논리 반경이 있다면 그 값에 맞춘다.**

왜 이렇게 요청하나요? “큰 거구에 원래 별도의 논리 반경이 있다면 그 값에 맞춘다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 원래 캐릭터의 특징을 가진 모델을 사용합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 16. 프레임의 기준점 통일

**아트 교체 전후의 발 위치, 몸체, 사거리와 모바일 실루엣을 비교한다.**

왜 이렇게 요청하나요? 걷기·공격 그림의 몸통 크기가 달라도 발은 같은 위치에 있어야 합니다. 기준점이 다르면 몸체는 정지해 있는데 그림만 튀거나 바닥을 미끄러지는 것처럼 보입니다.

#### 17. 구현할 결과와 조건 고정

**임시 도형이라도 겹치는 부품, 떠 있는 무기, 뒤집힌 면, 지나치게 많은 재질은 수정한다.**

왜 이렇게 요청하나요? “임시 도형이라도 겹치는 부품, 떠 있는 무기, 뒤집힌 면, 지나치게 많은 재질은 수정한다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 원래 캐릭터의 특징을 가진 모델을 사용합니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 18. 구현과 실행은 AI에게 맡기기

**코드·설정·파일 생성·실행은 네가 맡고, 필요한 화면과 결과를 보여 줘.**

왜 이렇게 요청하나요? 설명이나 코드 조각만 받으면 실제 파일 생성·연결·실행이 빠질 수 있습니다. AI가 개발 작업까지 수행하고, 사람은 요구·승인·결과 판단을 맡도록 역할을 분명히 합니다.

#### 19. 막힌 준비를 먼저 해결

**수행하지 못한 작업과 필요한 승인·도구 연결은 구분해서 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

왜 이렇게 요청하나요? 실패한 입력과 로그가 있어야 같은 문제가 다시 생겼을 때 비교할 수 있습니다. 성공 기록으로 덮어쓰지 않고 전후 자료를 남기면 무엇을 고쳤는지 확인할 수 있습니다.

<details>
<summary>보낼 원문 전체 — 설명은 복사되지 않습니다</summary>

```text
모델이 커 보인다고 공격 범위를 늘리지 마. VisualRoot만 교체하고 발·손 기준과 메시 크기를 맞춰 줘.
새 기능을 추가하지 말고 현재 오류와 실제 로그를 먼저 읽어 줘. 최소 수정 뒤 같은 재현과 관련 정상 동작을 다시 검사해 줘. 실패 기록은 지우지 마.
```

</details>

## 새 세션에서 이어가기

### AI에게 보낼 요구와 이유

#### 01. 이어서 할 작업 식별

**“같은 캐릭터를 실제 3D 모델로 만들기” 작업을 이어가고 싶어.**

왜 이렇게 요청하나요? 이름으로 재개할 작업을 찾고, 뒤에 이어지는 요청으로 실제 파일·진행 중 작업·기록을 다시 읽게 합니다. 제목만 보고 이전 상태를 기억한다고 가정하지 않습니다.

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

왜 이렇게 요청하나요? 대화가 끊겨도 외부 작업은 끝났거나 아직 실행 중일 수 있습니다. 프로세스·승인·미저장 상태를 먼저 읽어 같은 생성·빌드·결제를 두 번 시작하지 않도록 합니다.

#### 04. 되돌아갈 원본 남기기

**기존 성공과 실패 기록은 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

<details>
<summary>보낼 원문 전체 — 설명은 복사되지 않습니다</summary>

```text
“같은 캐릭터를 실제 3D 모델로 만들기” 작업을 이어가고 싶어. 실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘. 진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘. 기존 성공과 실패 기록은 보존해 줘.
```

</details>

## 왜 이렇게 만드는가

스프라이트를 판으로 세워 빌보드처럼 표시하는 것도 표현 방법이지만, 이번 3D 게임의 주 캐릭터 완성 기준은 아니다. 몸통·팔다리·무기·장비를 실제 3D 형태로 만든다. 같은 게임의 모험가·근접병·석궁수·거구·보스라는 정체성을 유지한다.

필수 경로는 Unity Editor 제작 도구로 단순 메시와 기본 도형을 조합하는 방법이다. 외부 3D 생성 서비스 결제를 필수로 추가하지 않는다. 원본 그림에 없는 후면 세부를 만들 때에는 기존 실루엣과 팔레트를 따르되, 새로 정한 디자인임을 기록한다.
