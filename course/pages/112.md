# 112. 네 역할을 순서대로 실행하기

**목표:** 작은 모의 작업이 역할 사이를 끝까지 지나갑니다.

**시작 상태:** 변경안 검사기

## 한눈에 보는 기능의 흐름

기획 결과 → 구현 후보 → QA 검사 제안 → 별도 검토

![네 역할을 순서대로 실행하기 — 개념 설명용 구조](../lesson_visuals/112.svg)

**경계:** 선행 역할 실패 뒤 후속 작업을 진행하지 않기

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“네 역할을 순서대로 실행하기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 변경안 검사기야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 구현과 판정의 책임 나누기

**고정된 모의 공급자로 기획→구현→QA→독립 검토를 순서대로 처리하는 실행기를 만들어 줘.**

왜 이렇게 요청하나요? 구현자가 자신의 설명만으로 완료를 결정하면 놓친 가정을 그대로 통과시킬 수 있습니다. 원래 요구·실제 변경·테스트를 다른 관점에서 검토하고 쓰기 권한을 나눕니다.

#### 02. 조회는 상태를 바꾸지 않게

**모의 응답이라는 표시를 요청·결과·대시보드에 유지해 줘.**

왜 이렇게 요청하나요? 진행 상황을 물을 때 새 구현이나 유료 호출이 시작되면 단순 확인이 실행 명령이 되어 버립니다. 저장된 근거를 읽어 완료·진행·승인 대기·미검증을 나누게 합니다.

#### 03. 구현할 결과와 조건 고정

**작업 상태는 대기·실행 중·제안 완료·검토 실패·막힘을 구분하고 선행 결과가 준비된 작업만 실행해 줘.**

왜 이렇게 요청하나요? “작업 상태는 대기·실행 중·제안 완료·검토 실패·막힘을 구분하고 선행 결과가 준비된 작업만 실행해 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 작은 모의 작업이 역할 사이를 끝까지 지나갑니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 04. 종료 이후의 상태까지 확인

**공급자 호출과 상태 저장의 경계를 나눠 공급자를 교체할 수 있게 해 줘.**

왜 이렇게 요청하나요? 현재 화면에서 맞는 값도 저장하거나 다시 구성할 때 빠질 수 있습니다. 실제 종료·불러오기 전후에 ID·옵션·장착·진행을 비교해야 유지되는 범위를 확인할 수 있습니다.

#### 05. 되돌아갈 원본 남기기

**한 작업이 실패하면 그 결과에 의존하는 작업을 멈추고 원본 오류를 보존해 줘.**

왜 이렇게 요청하나요? 새 구현이 실패해도 이전 게임과 저장을 복원할 수 있어야 합니다. 현재 내용을 먼저 조사하고 별도 후보에서 작업하면 실험이 유일한 정상본을 망가뜨리는 일을 피할 수 있습니다.

#### 06. 종료 이후의 상태까지 확인

**재실행 때 이미 완료한 같은 입력의 결과를 불필요하게 다시 만들지 마.**

왜 이렇게 요청하나요? 현재 화면에서 맞는 값도 저장하거나 다시 구성할 때 빠질 수 있습니다. 실제 종료·불러오기 전후에 ID·옵션·장착·진행을 비교해야 유지되는 범위를 확인할 수 있습니다.

#### 07. 관찰 가능한 기준으로 확인

**작은 피해 계산 함수와 테스트의 변경안을 처리하는 예를 만들고, 정상 흐름·중간 실패·응답 손상·중단 후 재개를 실제 실행해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 08. 구현할 결과와 조건 고정

**아직 Unity 게임이나 실제 Claude를 완료했다고 표시하지 마.**

왜 이렇게 요청하나요? “아직 Unity 게임이나 실제 Claude를 완료했다고 표시하지 마”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 작은 모의 작업이 역할 사이를 끝까지 지나갑니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 09. 설정과 실제 사용 결과 연결

**현재 작성한 MyGameHarness를 확장하고 필요한 파일·테스트·스킬 연결을 직접 만들어 실행해 줘.**

왜 이렇게 요청하나요? 데이터에 수치를 넣어도 사용 조건·UI·실제 전투가 그 값을 읽지 않으면 기능이 완성되지 않습니다. 선택 전후의 계산과 저장을 함께 확인합니다.

#### 10. 아래 항목을 완료 조건으로 사용

**정상 예와 실패 예를 실제로 보여 주고, 기존 기능이 유지되는지 확인해 줘.**

왜 이렇게 요청하나요? 요구사항의 목록은 AI에게 참고 설명을 주는 것이 아니라 완료를 판단할 기준을 정합니다. 구현 뒤 각 항목을 실제 입력과 결과에 대응시켜 빠진 조건을 찾습니다.

## 3. 결과를 직접 확인하기

### AI에게 보낼 요구와 이유

#### 02. 결과를 재확인할 근거 남기기

**정상 동작과 아래 실패 조건을 실제로 검사하고 대상·실행 수·결과를 보여 줘.**

왜 이렇게 요청하나요? “잘 됩니다”라는 요약만으로는 어떤 입력과 버전을 검사했는지 알 수 없습니다. 대상·실행 수·실패 내용·파일을 함께 남겨 같은 조건으로 다시 확인할 수 있게 합니다.

#### 03. 역할 사이의 입력을 실제로 전달

**네 역할의 의존 순서가 맞다.**

왜 이렇게 요청하나요? 역할을 여러 번 호출했다고 협업이 되는 것은 아닙니다. 선행 결과가 다음 작업의 입력이 되고 실패 시 후속 작업이 멈춰야 같은 기능을 일관되게 완성할 수 있습니다.

#### 06. 기존 결과를 보호

**원본 게임은 바뀌지 않는다.**

#### 07. 사람 검사의 시작점 준비

#### 08. 사람이 실제로 본 것만 기록

#### 09. 실제로 실행한 검사만 인정

## 새 세션에서 이어가기

### AI에게 보낼 요구와 이유

#### 01. 이어서 할 작업 식별

#### 02. 조회는 상태를 바꾸지 않게

**실제 프로젝트와 내 도구의 작업 기록을 읽고 어디까지 구현·검사됐는지 확인해 줘.**

#### 03. 재개 전 중복 작업 방지

**진행 중인 프로세스·승인·미저장 변경을 확인한 뒤 남은 가장 작은 작업부터 안내해 줘.**

## 왜 이렇게 만드는가

고정된 모의 응답은 실행 순서를 검사하는 장치다. 실제 AI가 독립적으로 판단했다는 증거는 아니다. 이 단계에서는 네 역할의 순서·대기·완료·오류 처리와 원본 보존을 확인한다.

완료한 작업을 다시 실행했을 때 외부 호출을 반복하지 않아야 한다. 이 성질을 확인한 뒤 실제 모델을 연결해야 재시작 한 번으로 같은 비용이 다시 생기는 일을 줄일 수 있다.
