# 050. 석궁수가 거리를 유지하게 만들기

**목표:** 원거리 적이 벽에 쏘거나 끝없이 도망치지 않습니다.

**시작 상태:** 근접 전투와 시야 판정

## 한눈에 보는 기능의 흐름

거리 확인 → 사선 확인 → 후퇴·측면 이동 → 멈춰 사격

그림은 실제 게임 실행 결과가 아닙니다. 값·규칙과 예제를 필요한 때 펼쳐 읽고 현재 단계의 메시지를 한 번씩 보냅니다.

## 1. 지금 상태 확인하기

첫 메시지를 보내 현재 준비 상태를 확인합니다. AI가 읽어 온 실제 프로젝트가 맞는지 보고, 없는 준비나 다른 상태가 있으면 먼저 알려 주세요. 아직 기능을 만들지 않는 단계입니다.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**“석궁수가 거리를 유지하게 만들기” 작업을 시작하기 전에 현재 상태를 읽기 전용으로 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 작업 대상부터 확인

**필요한 시작 상태는 근접 전투와 시야 판정야.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 03. 실제 사용 중인 구현 재사용

**실제 프로젝트와 작업 기록을 읽고 이것이 준비되어 있는지, 이미 같은 기능이 있는지 확인해 줘.**

왜 이렇게 요청하나요? 이름이 비슷한 새 클래스를 또 만들면 기존 화면은 여전히 옛 코드를 사용할 수 있습니다. 실제 호출되는 진입점을 찾아 연결해야 두 구현이 충돌하거나 수정이 반영되지 않는 문제를 막습니다.

#### 04. 현재 상태와 다음 확인 지점 구분

**이번 기능이 연결될 실제 파일·화면·도구와 보존할 기존 동작을 짧게 정리해 줘.**

왜 이렇게 요청하나요? 이미 준비된 기능과 아직 확인하지 못한 기능을 섞으면 불필요한 재설치나 성급한 완료 판정이 생깁니다. 현재 대상과 남은 준비를 나눠 가장 작은 다음 작업을 선택하게 합니다.

#### 05. 조사 단계에서 변경하지 않기

**아직 새 구현·설치·유료 호출·파일 변경은 하지 마.**

왜 이렇게 요청하나요? 현재 상태를 알아보기만 할 때 파일 변경이나 결제가 시작되면 검토 전의 환경이 바뀝니다. 준비 확인과 실제 구현을 나눠 되돌리기 어려운 작업이 먼저 실행되지 않게 합니다.

#### 06. 막힌 준비를 먼저 해결

**준비가 다르면 부족한 항목과 다음에 필요한 작업을 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 2. 필요한 기능 만들기

준비가 확인되면 아래 요청을 보냅니다. AI가 파일·설정·실행을 맡습니다. 변경 범위나 비용 승인이 나오면 내용을 읽고 결정하세요.

### AI에게 보낼 요구와 이유

#### 01. 작업 대상부터 확인

**현재 프로젝트의 실제 파일과 이미 결정한 규칙을 먼저 확인해 줘.**

왜 이렇게 요청하나요? AI가 다른 프로젝트나 오래된 예제를 보고 작업할 수 있습니다. 실제 경로·파일·현재 기능을 읽게 하면 지금 이어서 작업할 대상을 먼저 맞출 수 있습니다.

#### 02. 실제 사용 중인 코드에 연결

**이름이 다른 기존 구현이 있으면 새로 중복 제작하지 말고 그 구현에 연결해 줘.**

왜 이렇게 요청하나요? 예제와 이름이 다르더라도 현재 씬과 입력에서 호출하는 구현이 작업 대상입니다. 같은 기능을 새로 만들기보다 기존 진입점을 확인해 수정이 실제 게임에 반영되고 중복 실행되지 않게 합니다.

#### 03. 적이 아는 정보에 맞춰 행동

**원거리 적이 사격 거리와 시야를 확보하도록 행동 선택을 만들어 줘.**

왜 이렇게 요청하나요? 적이 플레이어의 실제 위치를 항상 읽으면 벽 뒤에 숨는 행동에 의미가 없습니다. 감지·기억·추적·귀환을 나눠 실제 관측 정보가 행동을 결정하게 합니다.

#### 04. 구현할 결과와 조건 고정

**무조건 뒤로 도망가다 벽에 끼지 않게 해 줘.**

왜 이렇게 요청하나요? “무조건 뒤로 도망가다 벽에 끼지 않게 해 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 원거리 적이 벽에 쏘거나 끝없이 도망치지 않습니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 05. 길찾기와 실제 도달을 구분

**현재 적의 사거리·이동 속도·공격 예고는 보존하고, 너무 가까우면 안전한 후퇴, 시야가 막히면 도달 가능한 측면 위치, 적당한 거리면 사격을 선택하게 해 줘.**

왜 이렇게 요청하나요? 목적지 표시나 경로 목록이 있다고 캐릭터가 끝까지 갈 수 있는 것은 아닙니다. 이동 가능한 경로와 실제 몸체의 진행을 확인하고 막힌 지점을 성공으로 표시하지 않게 합니다.

#### 06. 관찰 가능한 기준으로 확인

**후보 위치는 실제 경로·벽·몸체·화면 밖 거리로 검증하고, 작은 점수 변화마다 행동이 바뀌지 않도록 유지 시간과 전환 조건을 정해 줘.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 07. 구현할 결과와 조건 고정

**행동 후보와 점수·선택 이유를 디버그로 보여 줘.**

왜 이렇게 요청하나요? “행동 후보와 점수·선택 이유를 디버그로 보여 줘”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 원거리 적이 벽에 쏘거나 끝없이 도망치지 않습니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 08. 점이 아니라 몸체가 지나가게 하기

**벽 모서리·좁은 복도·주변 후보 전부 차단·플레이어 급접근을 실제로 시험해 줘.**

왜 이렇게 요청하나요? 길의 중심점이 연결돼 있어도 반경이 있는 캐릭터는 모서리나 좁은 문에 걸릴 수 있습니다. 실제 몸체 크기로 통과·차단을 확인해야 길찾기 그림과 플레이 결과가 맞습니다.

#### 09. 구현과 실행은 AI에게 맡기기

**코드·설정·파일 생성·실행은 네가 맡고, 필요한 화면과 결과를 보여 줘.**

왜 이렇게 요청하나요? 설명이나 코드 조각만 받으면 실제 파일 생성·연결·실행이 빠질 수 있습니다. AI가 개발 작업까지 수행하고, 사람은 요구·승인·결과 판단을 맡도록 역할을 분명히 합니다.

#### 10. 막힌 준비를 먼저 해결

**수행하지 못한 작업과 필요한 승인·도구 연결은 구분해서 알려 줘.**

왜 이렇게 요청하나요? 빠진 파일·권한·패키지를 있다고 가정하면 다음 구현이 엉뚱한 대상을 만들게 됩니다. 무엇이 없고 무엇을 먼저 해야 하는지 분리하면 불필요한 재작업을 줄일 수 있습니다.

## 3. 결과를 직접 확인하기

### AI에게 보낼 요구와 이유

#### 01. 검사할 입력과 관찰 지점 준비

**방금 구현한 기능의 자동 검사와 확인 화면을 준비해 줘.**

왜 이렇게 요청하나요? 정상 예 하나만 보면 실패 조건을 놓치기 쉽습니다. 정상·경계·반례를 실제 입력으로 준비하고 사람이 볼 화면도 맞춰 확인 범위를 분명하게 합니다.

#### 02. 결과를 재확인할 근거 남기기

**정상 동작과 아래 실패 조건을 실제로 검사하고 대상·실행 수·결과를 보여 줘.**

왜 이렇게 요청하나요? “잘 됩니다”라는 요약만으로는 어떤 입력과 버전을 검사했는지 알 수 없습니다. 대상·실행 수·실패 내용·파일을 함께 남겨 같은 조건으로 다시 확인할 수 있게 합니다.

#### 03. 관찰 가능한 기준으로 확인

**자동 검사: 후보가 모두 무효일 때 예외·NaN·무한 경로 요청이 없다.**

왜 이렇게 요청하나요? 구현 완료라는 설명을 실제 결과로 바꾸기 위한 조건입니다. 요청에 나온 대상과 경계 상황을 확인해 정상 결과뿐 아니라 실패를 어떻게 구분했는지도 남깁니다.

#### 04. 구현할 결과와 조건 고정

**같은 후보 점수는 ID 동점 규칙으로 결정된다.**

왜 이렇게 요청하나요? “같은 후보 점수는 ID 동점 규칙으로 결정된다”를 명시하면 AI가 무엇을 구현하거나 검사해야 하는지 범위를 좁힐 수 있습니다. 원거리 적이 벽에 쏘거나 끝없이 도망치지 않습니다. 이 결과를 확인할 때 이 조건이 실제로 반영됐는지 함께 봅니다.

#### 05. 구현할 결과와 조건 고정

## 이 작업에서 사용할 값과 규칙 전체

설계 시작값이며 측정된 성능·게임 성공 결과가 아닙니다. 구현은 AI가 수행합니다.

선호 사격 거리4~7m, 최소 이탈 거리2.5m로 시작한다. 후보는 현재 위치와 주변 8개, 총 9개다. 각 후보는 walkable/clearance를 통과하며 실제 몸체가 도달하는 완전한 A\* 경로가 있어야 한다. 유효 후보만 다음 점수로 비교한다.

`score = 3×LOS + 2×PreferredRange - 2×Crowding - 0.2×PathMeters - 3×Danger`

LOS·PreferredRange·Crowding·Danger는0~1로 정규화한다. Danger는 현재 보이는 위험 영역이나 방 바깥 등 **게임이 알려 준 정보**만 사용한다. 미래 플레이어 입력을 읽지 않는다. 새 후보가 기존보다0.5 이상 좋아야 갈아타고 최소0.6초는 현재 선택을 유지해 좌우 떨림을 줄인다.

발사 예고0.7초가 시작되면 조준을 확정한다. 발사점에서 벽까지 가려졌다면 발사를 취소하거나 벽에 맞는 결과를 일관되게 택한다. 기본은 Windup 시작 시 LOS 필요, 발사 후에는 첫 충돌이 벽이면 소멸이다. 투사체는 직전 위치→다음 위치 구간을 검사해서 빠른 탄이 얇은 벽을 뚫지 않게 한다.

## 왜 이렇게 만드는가

원거리 적에게 ‘플레이어와 거리가 가까우면 뒤로 이동’만 넣으면 벽이나 낭떠러지로 도망간다. 안전한 후보 위치를 먼저 만들고 후보별로 점수를 매긴다. 이 작은 점수식은 행동을 설명할 수 있고 모바일에서 실행 범위를 제한하기도 쉽다.

이 작업은 복잡한 범용 행동트리 프레임워크를 추가하는 장이 아니다. 상태기계는 유지하고, Chase/재배치 상태에서 **어디로 갈지**를 유틸리티 점수로 고른다. 무엇을 실행하는지는 Windup/Recovery가 계속 통제한다.
